# 사용자 이름·10만/5만 조회 범위·Keycloak 로그인 테마

적용일: 2026-10-17 · 독립 Infrastructure Monitoring Service

## 목적과 선택

사용자 이름을 `user1`, `user2`로 바꾸고 각각 Pod 100,000/50,000개를 조회하도록 합니다. 새로운 사용자별 데이터 복제나 Pod ID 권한 필터를 추가하지 않고 기존 Cluster 그룹 권한을 유지합니다.

| 계정 | 서버 권한 | Cluster | Namespace당 Pod | 총 Pod |
|---|---|---|---:|---:|
| admin | ADMIN | 전체 20개 | 아래 두 분포 합산 | 150,000 |
| user1 | VIEWER | 1~10 | 100 | 100,000 |
| user2 | VIEWER | 11~20 | 50 | 50,000 |

각 VIEWER는 Node 100개·Namespace 1,000개를 조회합니다. 운영 관측/경보는 ADMIN만 허용합니다. 사용자명 자체는 권한이 아니며 검증한 JWT의 client role/Cluster 그룹을 서버가 적용합니다.

## 데이터 보존과 이전 설치 이행

- ID 1~100000의 기존 Namespace·이름·상태·갱신 시각·재시작 수는 바꾸지 않습니다.
- 추가 ID 100001~150000의 기본 Namespace를 `((id-100001)/50)+1`로 바꿉니다. 첫 1,000개 Namespace에 50개씩 추가하여 원래 50개와 합산 100개가 됩니다. 뒤 1,000개는 원래 50개만 유지합니다.
- seed는 먼저 `ON CONFLICT DO NOTHING`으로 없는 행만 만들고, 기존 75,000/75,000 분포의 추가 fixture 행만 부모를 바꿉니다. 범위·기존 부모 공식·기본 생성 이름이 모두 일치하는 행만 대상이며 임의 사용자 행/이름/부모를 무조건 덮지 않습니다.
- 처음 업그레이드할 때 추가 행 49,975개의 부모가 바뀝니다. 첫 25개는 이미 같은 부모여서 변경하지 않습니다. 새 환경/재실행에서는 불필요한 변경을 하지 않습니다.
- 리소스/이력을 삭제하지 않고 상태/시간/재시작 필드도 덮지 않습니다. 이 작업은 fixture 소속 이행이며 Mock 상태 변경 이력을 새로 만들지는 않습니다. 기존 변경 이력은 리소스의 현재 소속에 따라 접근 범위가 바뀝니다.
- 현재 개발/runtime/인증 앱 DB 세 곳에 각각 적용하고 총 150,000·전반 100,000/후반 50,000과 기존 10만 부모 공식 위반 0을 확인했습니다. Keycloak identity DB에 seed를 실행하지 않았습니다.
- DDL/API/JPA 권한 모델은 같아 Flyway V1~V3를 수정하거나 새 스키마 마이그레이션을 추가하지 않았습니다. 이전 균등 분포의 성능 결과는 과거 측정값이며 새 분포 성능을 보장하지 않습니다.

이전 앱 DB에도 기존 [seed 실행 명령](../README.md)을 사용합니다. 이행은 각 DB의 한 트랜잭션으로 실행합니다. 이미 완료된 seed 컨테이너를 두고 이미지만 바꾸는 것만으로 기존 데이터를 자동 이전했다고 가정하지 않습니다.

## 계정과 비밀 설정

Keycloak Admin API에서 정확한 기존 사용자만 이름을 변경하여 같은 사용자 ID/sub·비밀번호·role/group을 유지했습니다. 충돌하는 새 이름이 있다면 임의 병합하지 않습니다. 이름 수정 제한으로 첫 변경이 거부되어 원복한 뒤, 관리 작업 동안만 이름 수정을 허용하고 원래 정책으로 복구했습니다. 사용자 셀프 변경 정책을 영구 해제하지 않았습니다.

Git 제외 credentials/realm 파일에도 이름을 동기화했습니다. 비밀번호는 이전에 요청한 로컬 데모 값을 유지하고 출력/문서/커밋에 넣지 않습니다. bootstrap/DB 암호와 다른 프로젝트 계정은 변경하지 않았습니다. 변경한 사용자 로그인 세션은 종료했으므로 다시 로그인합니다. 기존 JWT의 즉시 회수를 보장한다는 뜻은 아닙니다.

초기 생성 스크립트는 admin/user1/user2를 만들며 새 평가 환경의 공통 비밀번호는 `1234`입니다. CI 환경은 서로 다른 무작위 임시 비밀번호를 사용합니다. 사용 중인 Realm은 import만으로 덮어쓰지 않으므로 계정 이름만 소스에서 바꾸고 완료로 처리하지 않습니다. 공개 평가 계정 정책은 [인증 설계](AUTHENTICATION.md)에 정리합니다.

## 로그인 화면 구성과 안전 경계

`infra-monitor` 로그인 테마는 Keycloak 기본 `keycloak` 테마의 템플릿을 상속합니다. CSS·자체 SVG·한국어/영어 메시지만 추가합니다. 로그인 action·CSRF/인증 세션 처리·PKCE·비밀번호 표시 제어·오류 접근성은 Keycloak 기본 동작을 유지하고 별도 비밀번호 수집 폼/추가 JS를 만들지 않습니다.

- 서비스와 같은 흰색 카드·회색 배경·파란 버튼과 브랜드를 사용합니다.
- 좁은 화면·키보드 포커스·44px 입력/버튼·서버 오류를 검증합니다.
- 테마는 Compose에서 `/opt/keycloak/themes/infra-monitor:ro`로 읽기 전용 마운트합니다. 로컬/CI 양쪽에서 같은 소스 경로를 사용합니다.
- Realm에 loginTheme/표시 이름/지원 언어를 설정합니다. 브라우저 언어를 존중하며 기본 언어는 한국어입니다.
- 테마 마운트를 추가하기 위해 이 과제의 Keycloak 컨테이너만 재생성했습니다. identity DB/Realm/기존 볼륨·다른 프로젝트 Keycloak을 초기화하지 않았습니다. 앱 API/JWT issuer·audience·서명 정책은 그대로입니다.

로그인 화면은 [5176](http://127.0.0.1:5176/)에서 로그아웃 후 확인합니다. 기본 실행은 다음과 같습니다.

```bash
python3 scripts/auth-local.py
python3 scripts/test-auth.py
```

단, 첫 명령의 기존 전체 앱 이미지 빌드는 이번 작업에서 수행하지 않았습니다. 실제 적용에서는 Keycloak 서비스만 재생성하고 Admin API로 사용 중인 Realm을 변경했습니다. 이전 runtime 5175의 경보 미반영 문제는 별도이며 이번 테마 적용으로 해결했다고 주장하지 않습니다.

## 검증

- Gradle `test bootJar`: 서버 120개, 실패/오류/skip 0. 실제 DB의 이전 분포 이행·상태 보존·재실행·100/50 분포, Namespace 1000의 기존 50+추가 50 페이지·검색 경로, 15만 번째 ID의 VIEWER별 200/404, JPA SQL 횟수/Entity 로딩 경계를 검증합니다.
- Vitest 83개·vue-tsc·Vite build 통과. 실제 호스트 API+별도 프로덕션 preview의 읽기 전용 Chromium 10개 통과. DB를 직접 수정하는 폴링 E2E는 제외했습니다.
- 실제 Keycloak 브라우저 검증은 관리자/A/B 5개에 브랜드/한국어/키보드/1440px·320px 두 화면과 오류 후 재제출을 더해 8개입니다. 계정·토큰 trace를 저장하지 않고 캡처는 입력값 없는 로그인 폼만 저장합니다.
- 전체 Jenkins/새 앱 이미지·CI Keycloak 재생성·성능/FPS/작업관리자 메모리는 이번 범위에서 재실행하지 않았습니다. Testcontainers 공개 이미지용 클라이언트 분리로 개인 Docker 설정은 유지했습니다.
