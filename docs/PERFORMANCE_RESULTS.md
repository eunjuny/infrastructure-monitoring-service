# 성능 검증과 필수 개선 결과

기준일: 2026-10-14. Infrastructure Monitoring Service만 대상으로 작업했습니다. 기존 Auknowlog의 소스·DB·의존성은 변경하지 않았습니다. 커밋·푸시는 하지 않았습니다.

## 결론

실제 PostgreSQL의 Pod 100,000개에 연결한 프로덕션 화면을 CPU 4x·캐시 OFF로 측정했습니다. 초기 화면에서 불필요한 동기 레이아웃과 반복 날짜 계산을 줄였습니다. 최종 코드로 각각 새 Chromium을 실행한 20회씩 두 묶음에서 초기 진입·펼침·접기·검색·필터·갱신의 목표 초과는 없었습니다. 합성 프레임은 약 59.85FPS였습니다.

300MB 탭 메모리는 Chrome 작업관리자와 같은 지표로 측정하지 않았으므로 합격으로 단정하지 않습니다. 자동 갱신의 기능·선택·스크롤 유지도 검증했지만, 아래 지연 표의 갱신 수치는 수동 새로고침 이벤트 기준입니다. 전체 사용자·기기·검색어에 대한 성능 보장은 아닙니다.

서버와 DB는 기동된 상태이고 시뮬레이터는 계속 동작했습니다. SQL seed·서버 시작 시간은 진입 시간에 포함하지 않았습니다. 같은 묶음 안에서는 Chromium 프로세스를 재사용하므로 브라우저 최초 초기화와 이후 탐색을 구분합니다. 최초 진입은 Cluster 루트뿐 아니라 Pod 첫 목록과 전체 건수까지 표시하는 조건입니다.

측정 스크립트는 `frontend/scripts/measure-performance.mjs`, 재현 절차는 [프로토콜](PERFORMANCE.md)에 있습니다. 관측 코드는 테스트 브라우저에만 주입하며 제품 번들에 포함하지 않습니다. 중앙값은 짝수 표본의 가운데 두 값 평균, p95는 정렬된 표본의 `ceil(n × 0.95)`번째 값입니다.

## 확인한 문제와 적용 내용

### 1. 초기 가상 목록의 동기 레이아웃

마운트 시 `clientHeight`를 즉시 읽던 코드를 ResizeObserver의 콜백으로 대체했습니다. 관측 전에는 기본 높이를 사용하고, ResizeObserver가 없는 환경에서만 동기 측정을 합니다.

첫 필터 조회가 이미 맨 위인 목록에 다시 `scrollTop = 0`을 설정하던 작업도 생략했습니다. 실제로 스크롤했거나 처리 대기 중인 스크롤 RAF가 있을 때는 위치를 초기화하고 RAF를 취소합니다. 초기화 최적화 때문에 이전 필터의 위치가 새 결과에 남지 않도록 테스트했습니다.

### 2. 반복 날짜 계산

행마다 `Date.toLocaleString()`을 호출하던 전체 날짜 표시를 재사용하는 `Intl.DateTimeFormat`으로 바꿨습니다. 목록 tooltip과 상세의 날짜 형식은 유지하면서 반복 포매터 구성 비용을 줄였습니다.

### 3. 무한 요청 대기 방지

네트워크가 응답을 끝내지 않으면 서버 SQL의 3초 제한만으로는 브라우저 로딩을 종료할 수 없습니다. HTTP 요청마다 본문 JSON 처리까지 10초 제한을 적용했습니다. 시간 초과 안내와 재시도 경로를 제공하고, 사용자 취소는 시간 초과로 분류하지 않습니다. 성공·HTTP 오류·시간 초과·취소 후 타이머와 취소 리스너를 해제합니다.

이는 개별 HTTP 요청의 제한입니다. 여러 페이지를 순차 조회하는 갱신 그룹 전체가 10초 안에 끝난다는 뜻은 아닙니다. 상세 정책은 [화면 렌더링](FRONTEND_RENDERING.md), [자동 갱신](LIVE_UPDATES.md)에 있습니다.

|---|---:|---:|---:|---:|

중간 측정에서 목표를 초과한 첫 진입도 제외하지 않았습니다. 첫 브라우저 진입의 긴 메인 스레드 작업은 변경 전 320ms, 최종 두 묶음에서는 282ms·287ms였습니다. 포매터 재사용 후에도 summary 요청과 Pod 요청 시작 사이에 약 131ms의 간격이 있었고, 불필요한 스크롤 초기화 제거 후 최종 1차에서는 약 2ms로 줄었습니다. 화면의 초기 동기 작업을 줄인 방향과 일치하지만 브라우저 초기화·OS·DB 변동이 있으므로 개별 변경의 성능 기여율을 확정하지 않습니다.

검색은 중간 측정마다 변동했습니다. 마지막 두 묶음의 검색 중앙값은 약 103ms·117ms로 변경 전 약 51ms보다 높았습니다. 모두 300ms 목표 이내지만 검색 성능까지 개선됐다고 설명하지 않습니다. DB 시뮬레이터와 인덱스의 상태를 고정한 추가 분석 없이 원인을 단정하지 않습니다.

## 스크롤·메모리와 반복 탐색

4초 연속 스크롤에서 `DirectRenderer::DrawFrame` trace event는 각 묶음 240개였고 합성 프레임률은 59.85FPS였습니다. RAF 빈도는 약 60FPS, 33.4ms 초과 간격은 0회였습니다. 이는 500행 이동 창의 실제 DOM 스크롤이며 100,000개 DOM을 만든 측정이 아닙니다. 첫 페이지부터 실제 DB의 10만 Pod를 순차 탐색할 수 있지만 임의 위치 점프는 제공하지 않습니다.

추가 100페이지·10,000개를 탐색한 동안 캐시는 500개, 목록 DOM은 14~20행을 유지했습니다. 아래는 최종 2차의 기록입니다.

| 추가 페이지 | 보관 행 | 렌더 행 | JS heap, MiB | renderer RSS, MiB |
|---|---:|---:|---:|---:|
| 0 | 500 | 20 | 7.11 | 263.17 |
| 25 | 500 | 14 | 9.35 | 260.86 |
| 50 | 500 | 14 | 9.49 | 259.98 |
| 75 | 500 | 14 | 9.69 | 268.11 |
| 100 | 500 | 14 | 14.73 | 274.84 |

최종 1차의 renderer RSS 최고 관측값은 287.16MiB였고 추가 100페이지 후 JS heap은 13.23MiB였습니다. 두 묶음의 강제 GC 이후 heap은 각각 약 4.43MiB였습니다. 강제 GC는 보조 진단이며 일반 실행의 메모리 값 대신 사용하지 않습니다. 이 짧은 반복 실험에서 전체 탐색 항목이 계속 보관되는 현상은 확인하지 않았지만 장기 메모리 누수 부재를 증명한 것은 아닙니다.

RSS는 renderer 프로세스의 물리 메모리, JS heap은 JS 객체 영역입니다. 가이드의 Chrome 작업관리자 탭 메모리와 동일하지 않으며 MiB와 십진 MB도 다릅니다. 따라서 300MB 기준은 실제 작업관리자에서 추가 확인해야 합니다.

## 실제 DB 실행 계획

`scripts/explain.sql`은 읽기 전용 대표 쿼리입니다. 경로 join은 포함하지만 API 전체 응답과 투영 열·정렬 표현이 동일하지 않으므로 아래 시간을 API 지연으로 대체하지 않습니다. PostgreSQL 17.11, 10만 Pod·동작 중인 mock 프로필에서 한 번 확인한 값입니다.

| 조회 | 주요 접근 | 실행 시간 | 결과 |
|---|---|---:|---:|
| 선택적인 이름 검색 | idx_pod_name_trgm Bitmap Index/Heap Scan | 39.506ms | 1행 |
| ERROR 첫 페이지 | idx_pod_status_id Index Scan | 0.259ms | 101행 |
| ID > 99,000 커서 | Pod 기본 키 Index Scan | 0.190ms | 101행 |
| 한 글자 미일치 `%z%` | Pod Seq Scan, 100,000행 확인 | 40.273ms | 0행 |
| 정확한 전체 건수 | Pod Seq Scan | 9.902ms | count 100,000 |

101행은 다음 페이지 여부를 확인하는 `limit + 1`입니다. 현재 정상적인 검색·필터·갱신에서 DB 스키마 변경을 요구할 병목은 확인하지 않았습니다. 이름 GIN은 모든 단문·흔한 검색어에 효과적인 것이 아니며 건수 집계는 폴링 대상에서 제외합니다.

- `npm run build`: 타입 검사·프로덕션 빌드 통과.
- `npm run test:e2e`: 실제 PostgreSQL·API Chromium 7개 통과. 탐색·검색·필터·캐시·자동 반영·선택·스크롤 유지·콘솔 조작·모바일 레이아웃을 재확인했습니다.
- `npm audit --audit-level=moderate`: 0건.
- 백엔드 소스·API·스키마는 이번 개선에서 변경하지 않았습니다. 앞서 전체 69개, 실제 PostgreSQL 통합 17개를 통과한 상태이며 이번에 백엔드 전체 테스트를 다시 실행한 것은 아닙니다.

## 남은 제출 전 점검

1. 실제 Chrome 작업관리자 탭 메모리와 headful 수동 스크롤 기록을 확인합니다.
2. 자동 폴링 요청 시작부터 변경 표시까지도 별도 지연 기록을 남깁니다. 현재 자동 반영은 기능 E2E로 검증했습니다.
3. 한 글자·흔한 부분 문자열·모든 유형 검색·여러 부모 동시 펼침에서 반복 성능을 확인합니다.
4. 가이드가 순차 커서가 아니라 전체 10만 행의 자유로운 위치 이동을 기대하는지 최종 점검합니다. 현재 UX를 임의 인덱스 점프라고 설명하지 않습니다.

추가 OSS·캐시·DB 인덱스는 측정 근거 없이 늘리지 않았습니다. 성능 원본 trace는 Git 제외 경로 `frontend/.validation/performance/*-trace.json`, 실행 계획 원문은 `.validation/explain-results.txt`에 있습니다. 제출 가능한 핵심 측정 배열은 위 JSON 링크에 보관했습니다.
