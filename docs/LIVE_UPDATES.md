# Mock 상태 변경과 자동 갱신

## 목적과 범위

상태가 고정된 대량 목록만으로는 갱신 시 선택·스크롤 유지와 장애 처리를 확인하기 어렵습니다. 현재 기본 규모는 Pod 15만 개이며 선택형 서버 시뮬레이터가 실제 과제 DB의 작은 배치를 변경하고, 화면은 현재 조회 범위를 재조회합니다. 실제 Kubernetes와 연결하거나 상태를 추론하는 기능이 아닙니다. 별도 Redis·메시지 브로커·WebSocket은 사용하지 않습니다.

```text
mock 프로필 → 초기 10초 대기 → ID 커서로 제한 행 선택·잠금
→ 4개 유형의 상태·속성 UPDATE + 변경 이력 INSERT → 전체 배치 COMMIT → 커서 전진
→ 5초 후 다음 배치

화면 초기 조회 → 완료 후 5초 대기 → 현재 창·펼친 계층·선택 상세 GET
→ 변경 없는 행 재사용·변경 행 같은 키로 교체 → 선택·스크롤 유지
실패 → 기존 화면 유지·안내 → 최대 60초 백오프
숨김·오프라인·해제 → 타이머·진행 중 자동 요청 취소
```

## 서버 시뮬레이터

상세의 Node Ready/Pressure·Pod phase/준비/문제 사유는 기존 현재 상태에 연결된 [Mock 진단 시나리오](RESOURCE_DIAGNOSTICS.md)로 계산합니다. 시뮬레이터가 상태를 바꾸면 다음 상세 조회에 함께 반영되며 별도 조건 컬럼을 쓰지 않습니다. 기존 상태/사용률/재시작 이력 계약은 유지하고 과거 컨테이너 정보를 새로 만들어 이력에 넣지 않습니다. 상세가 선택된 경우 폴링에 그 Cluster/Namespace의 전체 하위 범위 집계도 포함되지만 전역 유형별 건수는 여전히 폴링하지 않습니다.

기본 `monitoring.mock.enabled=false`에서는 상태 변경 스케줄러가 생성되지 않습니다. 이력 보관 정리 스케줄러는 기본 모드에서도 실행합니다. `mock` 프로필에서 상태 변경을 활성화하며 `MOCK_UPDATES_ENABLED=false`로 다시 끌 수 있습니다. `MOCK_UPDATE_INTERVAL_MS`는 1,000~60,000ms만 허용하고 기본 5,000ms입니다. 초기 지연은 기본 10초입니다. 주기는 배치 완료 후부터 계산합니다.

| 유형 | 한 번에 최대 | 변경 |
|---|---|---|
| Cluster | 1개 | 상태·갱신 시각 |
| Node | 5개 | 상태·갱신 시각·CPU·메모리 |
| Namespace | 10개 | 상태·갱신 시각 |
| Pod | 100개 | 상태·갱신 시각·오류 전환 시 재시작 수 |

- `id > 마지막 ID ORDER BY id LIMIT ... FOR UPDATE`로 기본 키 기반 제한 배치를 선택합니다. 끝에서는 첫 ID로 돌아갑니다. 전체 15만 객체를 메모리에 로딩하거나 매번 전체 건수를 세지 않습니다.
- 상태는 NORMAL → WARNING → ERROR → NORMAL을 순환합니다. Node CPU·메모리는 범위 0~100을 유지하고 Pod 재시작 수는 int 최대값에서 포화시킵니다.
- 네 유형의 한 배치를 하나의 트랜잭션으로 처리하고 커밋이 끝난 후에만 메모리 커서를 전진합니다. 실패하면 이전 유형의 변경도 롤백하고 같은 커서부터 재시도합니다.
- JPA 전환 후에는 JpaTransactionManager 아래 EntityManager native CTE를 사용합니다. dirty checking으로 116개 Entity를 갱신하는 방식으로 바꾸지 않았습니다. bulk DML 전 flush·후 clear로 영속성 컨텍스트와 DB 상태 충돌을 피합니다. [JPA/native 경계](JPA_QUERY_DESIGN.md#변경과-이력-jpa-native-query-경계)를 참고합니다.
- 같은 트랜잭션에서 변경 전후 상태·속성을 `resource_change_event`에 기록합니다. 발생원은 Mock이며 실제 Kubernetes Event나 장애 원인이 아닙니다. 이력은 전체 최신 20,000개·24시간 이내로 제한하고 60초마다 최대 5,000개를 정리합니다. [보관·조회·검증](OPERATIONS_AND_DELIVERY.md#2-상태속성-변경-이력)을 참고합니다.
- HTTP 변경 API는 없습니다. 스케줄러는 단일 프로세스용입니다. 여러 백엔드 인스턴스의 리더 선출·분산 스케줄링을 제공하지 않습니다.
- 변경량을 제한해 리소스를 순차 순환합니다. 보고 있는 Pod가 해당 배치에 포함될 때만 값이 바뀝니다. 모든 화면 행이 5초마다 반드시 변경되는 것은 아닙니다.
- Pod 150,000개에서 한 번에 100개씩 처리하므로 한 순환은 1,500배치입니다. 처리 시간을 제외한 약 125분이며, 특정 Pod가 5초마다 바뀐다는 뜻이 아닙니다. 배치 상한은 확장 후에도 유지합니다. [순서별 학습 설명](STUDY_QUESTIONS.md)에 Mock와 운영 지표의 차이를 정리합니다.
- 로그에는 오류 클래스만 남기고 SQL·접속 정보·예외 내부 메시지를 출력하지 않습니다. 이 프로필은 과제 DB 전용입니다.

## 화면 폴링 정책

현재 보관한 목록 최대 5페이지·500개, 루트 및 펼친 부모 최대 9페이지, 선택 상세 1개만 재조회합니다. 자동 폴링 한 그룹은 조회 창에 따라 약 2~15회의 GET을 사용하며 전체 건수 집계는 포함하지 않습니다. 최대 캐시·응답 크기는 [화면 설계](FRONTEND_RENDERING.md)를 따릅니다.

- 초기 조회나 사용자 입력·상세 요청 중에는 기다립니다. 요청 그룹 종료 후 다음 타이머를 예약하여 느린 요청이 겹치지 않습니다.
- 같은 조건에서는 응답을 모아 한 번에 교체하고 기존 행 키와 변경 없는 객체를 재사용합니다. 새 필터는 커서를 초기화합니다.
- 실패 시 기존 데이터·선택·스크롤을 유지하고 오류를 표시합니다. 재시도는 10·20·40·60초로 늘어나며 성공하면 5초로 돌아갑니다.
- 각 HTTP 요청은 JSON 본문 처리까지 10초 제한을 적용합니다. 응답이 멈춰도 무한 로딩에 남지 않고 시간 초과 안내와 재시도를 제공합니다. 사용자 취소는 시간 초과와 구분하고 타이머·취소 리스너를 정리합니다. 5페이지 순차 갱신 전체의 10초 제한은 아니며, 서버의 쿼리별 3초 제한과도 다른 경계입니다.
- 숨긴 탭·오프라인에서는 중지하고 진행 중 자동 요청을 취소합니다. 취소를 서버 오류로 세지 않습니다. 복귀 시 타이머를 중복 생성하지 않습니다.
- 체크박스로 자동 갱신을 해제하거나 다시 켤 수 있습니다. 컴포넌트 해제 시 타이머와 이벤트 리스너를 정리합니다.
- 변경분 전용 스트림이 아닌 제한된 기존 API 재조회입니다. 서버 변경부터 다음 폴링까지의 대기와 응답·렌더링 지연은 별도 수치입니다. 5초 간격은 과제의 200ms 갱신 반영 목표를 달성했다는 의미가 아닙니다.
- 운영 관측 메뉴에서는 리소스 정기 폴링을 중지합니다. 운영 지표는 별도 고정 PromQL API로 조회하며 서버 HTTP·목록/검색 SQL·Mock 배치의 지연과 변경·실패 Counter를 표시합니다. Mock CPU 값과 실제 JVM·DB 연결 지표를 구분합니다.

## 검증

Testcontainers에서 실제 SQL의 제한 변경·속성·부모 관계·오류 전환·롤백을 확인했습니다. 단위 테스트로 스케줄러 비활성 기본값·간격 제한·커서 전진·실패 재시도를 검증했습니다. 프론트 테스트는 중복 요청·숨김·오프라인·해제·백오프를 검증합니다. 실제 Chromium에서는 DB의 Pod 상태를 변경한 뒤 자동 반영과 선택·1,200px 스크롤 유지를 확인했습니다. [실행 결과](STAGE4_REPORT.md)를 참고합니다.

추가 측정에서는 목록 500개·펼친 부모 8개·선택 상세를 유지한 최대 조회창에서 실제 15개 GET의 자동 갱신 그룹을 관측합니다. 첫 요청부터 변경값과 그룹 완료가 표시될 때까지의 지연, DB 변경 확인부터 다음 요청까지의 폴링 대기를 별도로 기록합니다. [측정 방식](PERFORMANCE.md#추가-검색계층자동-갱신-측정), [실제 결과](PERFORMANCE_EDGE_RESULTS.md)를 참고합니다.
