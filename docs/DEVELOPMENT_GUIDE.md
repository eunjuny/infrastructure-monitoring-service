# 개발 가이드라인

적용 범위: Infrastructure Monitoring Service 전체 저장소 · 제정: 2026-10-14

## 1. 목적과 적용 방법

기능이 늘어나도 구조·안전·성능·검증 근거가 유지되는 개발을 목표로 합니다. 별도 유료 서비스나 AI 프레임워크 없이 저장소 지침, 테스트, 자동 검사, CI로 구성합니다. 이를 이 프로젝트의 **개발 하네스**라고 부릅니다. 하네스는 AI가 코드를 작성한다는 뜻이 아니라, 사람과 AI 모두가 따라야 할 작업 환경·제약·피드백 체계입니다.

작업 시작 시 [AGENTS.md](../AGENTS.md) → 이 문서 → [현재 구조](PROJECT_GUIDE.md) → 해당 주제 문서 순으로 확인합니다. 변경 전 현재 diff와 관련 테스트를 읽고 작업 범위를 정합니다. 단순 질의응답에는 이 절차 전체를 강제하지 않습니다.

- **필수**: 어기면 수정하거나 명시적인 설계 변경·검증이 필요합니다.
- **권장**: 현재 문제를 단순하게 해결하는 기본 선택입니다. 이유가 있으면 다르게 할 수 있습니다.
- **자동 검사**: [품질 게이트](QUALITY_GATES.md)가 일부 필수 규칙을 검사합니다. 검사를 통과해도 모든 규칙을 충족하거나 보안상 안전하다는 뜻은 아닙니다.
- 적용은 신규·변경 코드부터 시작합니다. 기존 코드를 스타일만으로 일괄 재작성하지 않으며, 기존 예외는 아래 개선 목록에 남깁니다.

## 2. 설계와 범위

**필수**

1. 과제 요구사항을 우선합니다. 실제 Kubernetes 연동·조직 단위 멀티 테넌시·MSA 등 미구현 범위를 구현한 것처럼 설명하지 않습니다. 선택형 Keycloak의 구현/제약은 [인증 설계](AUTHENTICATION.md)와 구분해 설명합니다.
2. 새 기능·OSS는 해결할 문제, 기존 방식의 부족함, 대안, 비용/운영 부담, 검증 방법을 먼저 적습니다. 채용 키워드만을 이유로 도입하지 않습니다.
3. 호환되지 않는 API/스키마/운영 변경은 영향·이행·복구 절차를 설계합니다. 되돌릴 수 없는 작업을 임의 실행하지 않습니다.
4. 한 변경은 하나의 목적을 갖게 합니다. 기능 개발과 대규모 포맷 변경·관련 없는 리팩터링을 섞지 않습니다.
5. 새로운 추상화는 중복된 실제 요구가 있을 때 추가합니다. 이 과제에서는 기능별 패키지와 단일 애플리케이션을 기본으로 유지합니다.

중요한 결정은 기준 문서 또는 주제 문서에 **문제 → 대안 → 선택 이유 → 제약 → 검증** 순으로 남깁니다. 작은 변경마다 별도 ADR 파일을 만들 필요는 없습니다.

## 3. 소스 구조와 책임

```text
backend/.../resource     탐색 API·검증·커서·DTO·조회
backend/.../persistence  JPA Entity와 관계 매핑
backend/.../mock         배치 정책·스케줄링·원자적 변경
backend/.../history      변경 이력 조회·보관 정책
backend/.../operations   고정 PromQL·관측 응답
frontend/src/api.ts      HTTP·응답 타입·요청 제한
frontend/src/use*.ts     조회 상태·폴링 등 재사용 상태 로직
frontend/src/components 화면 컴포넌트·사용자 상호작용
scripts/                seed·검증·CI·실행 도구
infra/                  Prometheus·Jenkins 설정
docs/                   현재 설계·검증 근거·누적 이력
```

| 경계 | 책임 | 피할 것 |
|---|---|---|
| Controller | HTTP 입력·응답 변환, 서비스 위임 | 직접 SQL/EntityManager, 정책 분산, Entity 반환 |
| Service | 유스케이스·관계 검증·트랜잭션·정책 | HTTP 응답 조립 책임 혼합, 행별 반복 DB 호출 |
| Repository | 바인딩 쿼리·DTO 조회·제한된 변경 | 사용자 입력의 SQL 연결, 무제한 조회·삭제 |
| Entity | 저장 구조와 관계 | JSON API 계약 노출, 컬렉션 무분별한 EAGER 로딩 |
| UI 컴포넌트 | 표시·이벤트·접근성 | 개별 fetch, 서버 정책 복제, 외부 HTML 실행 |
| 상태 로직 | 요청 수명·최신 응답·캐시·폴링 | 무제한 캐시, 중복 폴링, 해제되지 않는 타이머 |

단순 위임만 하는 형식적인 Service를 무조건 추가하지는 않습니다. 다만 입력 검증·응답 조립·저장 조회가 커지면 Controller에서 유스케이스로 분리합니다. 현재 예외는 12절에 기록합니다.

## 4. 코드 작성과 가독성

- 백엔드 빌드는 저장소 Gradle Wrapper와 Kotlin DSL·strict lockfile을 사용합니다. 전역 Gradle/Maven에 의존하거나 별도 POM을 다시 추가하지 않습니다. 버전 갱신·실행·보고서 경로는 [Gradle 가이드](GRADLE_BUILD.md)를 따릅니다.
- Java 4칸, Vue/TypeScript/CSS/YAML 2칸, Python 4칸, UTF-8·LF·파일 끝 개행을 기본으로 합니다. [EditorConfig](../.editorconfig)를 사용합니다.
- 한 줄에 여러 정책·분기·비동기 작업을 압축하지 않습니다. 의미 있는 변수명, 한 책임의 메서드, 명시적인 import를 우선합니다. 주석은 코드 번역보다 이유·제약을 설명합니다.
- 오류를 무시하는 빈 catch, 원인 없는 기본값 대체, 테스트만 통과시키는 예외 처리를 금지합니다. 외부에는 안전한 오류를 반환하고 내부에서는 원인을 추적 가능하게 유지합니다.
- API 입력·응답은 명시적 DTO/타입으로 표현합니다. 새 코드에 `@ts-ignore`·`@ts-nocheck`를 추가하지 않습니다. `unknown`은 검증/축소 후 사용하며 `any`로 계약 오류를 숨기지 않습니다.
- 기존 파일 전체 포맷 변경은 별도 작업으로 수행합니다. 현재 자동 게이트는 포매터가 아니며 import 순서·들여쓰기 폭·복잡도를 완전 검사하지 않습니다.

## 5. API와 데이터 처리

**필수**

- 브라우저 검증과 별개로 서버에서 유형·ID·limit·검색어·범위 소속·커서 조건을 검증합니다.
- 잘못된 입력 400, 없는 리소스 404, 일시적인 의존 장애 503 등 기존 계약과 오류 형식을 유지합니다. SQL·스택·시크릿을 응답에 포함하지 않습니다.
- 목록/검색 최대 100개, 다음 페이지 판단용 내부 합산 101개, 순차 keyset 방식을 유지합니다. 필터 변경 시 커서를 초기화합니다. 상한 변경은 근거·성능 테스트와 문서 변경이 필요합니다.
- 쿼리는 바인딩합니다. 동적 유형·정렬·테이블 선택은 서버의 enum/허용 목록만 사용합니다. 부분 검색의 와일드카드 의미를 의도적으로 처리합니다.
- 전체 count는 초기 조회와 별도60초 이상의 만료 주기에 사용하고5초 상태 폴링마다 반복하지 않습니다. 하나의 갱신 작업 안에서 중복을 막고 숨김·오프라인·해제 정책을 공유합니다.
- SQL별 3초와 클라이언트 요청별 10초는 서로 다른 경계입니다. 전체 요청 제한이라고 잘못 설명하지 않습니다.
- API 변경은 [API.md](API.md), 클라이언트 타입, 성공·실패 테스트를 함께 변경합니다.

## 6. JPA·스키마·트랜잭션

- 운영 코드는 JPA/EntityManager를 사용합니다. Testcontainers fixture 및 독립 검증용 JDBC는 허용합니다.
- OSIV off, ddl-auto validate, Flyway의 스키마 소유권을 유지합니다. 이미 커밋한 V1~Vn은 수정·삭제하지 않고 다음 마이그레이션으로 변경합니다.
- 읽기는 필요한 열의 DTO projection과 readOnly를 우선합니다. Entity 그래프 직렬화·목록의 컬렉션 fetch join 페이지 처리를 피합니다. 관계는 LAZY를 기본으로 합니다.
- N+1은 추측이 아니라 실제 PostgreSQL의 SQL 횟수·Entity/컬렉션 로딩으로 검증합니다. H2 결과로 PostgreSQL 방언·인덱스·JSONB 검증을 대체하지 않습니다.
- PostgreSQL 전용 native CTE는 원자적 배치처럼 이유가 있는 위치에서 허용합니다. 바인딩·timeout·배치 상한·flush/clear·실패 롤백을 검증하고 이유를 문서화합니다.
- Mock 리소스 변경과 이력은 같은 트랜잭션입니다. 커서와 성공 지표는 커밋 확인 뒤에만 갱신합니다. 배치·보관 정리는 기존 상한을 유지합니다.
- 운영 데이터 손실을 일으킬 seed/정리/성능 테스트는 과제 DB에서만 실행합니다. 볼륨 삭제나 데이터 초기화는 일반 검증 절차가 아닙니다.

구체적인 쿼리 선택과 SQL 예산은 [JPA 설계](JPA_QUERY_DESIGN.md), 배치·보관은 [운영 설계](OPERATIONS_AND_DELIVERY.md)를 기준으로 합니다.

## 7. 프론트엔드·성능·접근성

- HTTP 호출은 api.ts를 통합니다. 이전 요청 abort와 응답 revision 검증을 유지합니다. 화면 이탈·unmount에서 타이머/요청을 정리합니다.
- 자동 갱신은 중복 실행하지 않고 숨김·오프라인에서 중지하며 실패 시 백오프합니다. 오류 때 기존 데이터·선택·스크롤을 보존합니다.
- 목록 500개·5페이지, 트리 24페이지·동시 펼침 8개 등 현재 자원 상한을 유지합니다. DOM은 가상화된 행만 렌더링합니다. 변경 시 실제 DB E2E와 성능을 재측정합니다.
- 상세·운영·이력은 사용 시 코드 로드하고 초기 조회 3개와 불필요한 추가 요청을 구분합니다. 초기 진입에 큰 라이브러리·지역화 초기화를 다시 추가하지 않습니다.
- 날짜의 원본 ISO/시간대 의미를 유지합니다. 화면 시간 형식과 안전한 건수 표시는 공통 유틸리티를 우선 사용합니다.
- 외부 문자열은 텍스트로 표시합니다. `v-html`·innerHTML 대입·eval·동적 Function 실행은 금지합니다. 불가피한 요구는 별도 보안 설계가 먼저입니다.
- 버튼/입력의 이름·label·포커스·키보드 동작, 로딩/빈 결과/오류/재시도, 모바일 레이아웃을 검증합니다. 색상만으로 상태를 구분하지 않습니다.
- 성능 변경은 같은 데이터·CPU/cache·준비 조건으로 전후를 비교합니다. 느린 첫 표본을 버리거나 준비 조건을 줄이지 않습니다. 프레임·탭 메모리·서버/API 지연을 혼동하지 않습니다.

## 8. 보안·운영·관측

- API 키·실제 비밀번호·토큰·개인 URL·실사용 이메일을 코드/문서/테스트/출력에 남기지 않습니다. 로컬 시크릿은 Git 제외 파일에 보관하고 값 대신 존재·권한만 확인합니다. 공개 평가용 세 계정의 고정 비밀번호 `1234`는 사용자 요청의 테스트 데이터 예외입니다. DB·Keycloak 초기화 관리자·내부 제어 토큰 및 CI 계정은 무작위 생성 정책을 유지합니다.
- 인터넷 공개는 별도 인증·TLS 설계가 필요합니다. 로컬 루프백과 내부 Compose 네트워크를 유지합니다. 관리 포트·DB를 웹 프록시로 공개하지 않습니다.
- 인증 환경의 JWT issuer·audience·서명·시간·sub와 API client role을 검증하고 모든 조회/집계에 서버의 Cluster 권한을 적용합니다. 사용자명·브라우저 clusterId로 권한을 결정하지 않으며 인증 실패에 비인증 모드로 fallback하지 않습니다. 기본 비인증 모드는 별도 루프백 데모만 허용합니다.
- Prometheus는 서버의 고정 URL/PromQL만 허용하고 리다이렉트·본문 크기·수신 시간·반환 점수 상한을 유지합니다. 임의 사용자 URL 요청을 추가하지 않습니다.
- 지표 라벨은 제한된 유형·동작·성공 여부만 사용합니다. ID·이름·검색어로 고카디널리티를 만들지 않습니다. 값 없음과 장애를 가짜 0/DB 값으로 대체하지 않습니다.
- 예외·로그에 사용자 입력/응답 본문을 무제한 덤프하지 않습니다. 저장·캐시·요청·로그·보관량은 상한을 갖게 합니다.
- 컨테이너 비루트·다단계 빌드·빌드 컨텍스트 제외를 유지합니다. Jenkins 호스트 agent는 신뢰하는 코드 전용이며 임의 PR 실행을 허용하지 않습니다.
- 외부 AI/유료 API·클라우드 자원·SMTP 전송·외부 공개·파괴 작업은 일반 테스트로 실행하지 않습니다. 사용자 요청 범위를 먼저 확인합니다.

## 9. 테스트와 변경 위험

| 변경 | 최소 확인 |
|---|---|
| 문서/지침/검사 도구 | 빠른 게이트·도구 회귀 테스트·링크/내용 확인 |
| 서버 정책/커서/DTO | 단위/MVC·실제 DB 영향 테스트·API 문서 |
| JPA/쿼리/마이그레이션 | 실제 PostgreSQL 매핑·SQL 횟수·정합성·인덱스/timeout·롤백 |
| 화면/조회 상태 | Vitest·타입·빌드·관련 실제 API E2E·모바일/키보드 |
| 캐시/가상화/초기 로딩 | 위 검증 + 동일 조건 전후 성능·자원 상한 |
| Compose/CI/관측 | 구성 검사·관련 실패 테스트·격리 runtime·실제 수집/정리 |

테스트는 결과와 안전 경계를 검증합니다. 단위 테스트의 대체 응답과 실제 API E2E를 구분하며, 실패 시 원인을 고친 뒤 재실행합니다. 테스트를 지우거나 기준을 낮춰 통과시키지 않습니다. 실행하지 못하면 이유와 남은 검증을 명시합니다. 최신 실행 개수는 [기준 문서](PROJECT_GUIDE.md), 명령과 단계는 [품질 게이트](QUALITY_GATES.md)를 참고합니다.

## 10. 작업 루프와 완료 기준

1. **착수**: 사용자 요청, git status/diff, AGENTS·현재 설계·관련 테스트를 확인합니다. 기존 변경은 보존합니다.
2. **계획**: 수정 파일·데이터/API 영향·안전 경계·검증 범위를 정합니다. 불명확한 제품 결정이나 추가 비용은 확인합니다.
3. **구현**: 작은 변경으로 진행하고 결함 수정에는 재현 테스트를 추가합니다. 같은 목적의 문서·타입·계약도 갱신합니다.
4. **검증**: 빠른 게이트 → 위험도에 맞는 테스트 → 필요 시 실제 DB/브라우저/성능/CI 순으로 실행합니다. 프로세스만 띄운 것을 검증 완료라고 하지 않습니다.
5. **기록**: PROJECT_GUIDE와 주제 문서, 실행 방법 변경 시 README, 모든 유의미한 작업은 WORK_HISTORY에 추가합니다. 기존 실패 기록을 보존합니다.
6. **자체 리뷰**: 동작·경계·보안·자원 상한·예외 처리·테스트 독립성·문서 일치와 diff를 확인합니다. 새 의존성·대규모 재작성·시크릿이 없는지 확인합니다.

CI 실행자는 Jenkins 하나로 유지하며 전체 Git SHA를 별도 공간에 체크아웃합니다. 미커밋 파일을 CI 입력으로 사용하지 않으며 새 체크아웃에서 단계별 소스·이미지·컨테이너 근거를 확인합니다. 실행 중인 체크아웃/이미지를 수정하지 않습니다. 개발 폴더의 후속 수정은 기존 CI에 포함되지 않으므로 새 커밋/빌드로 검증합니다. 로컬 재현용 스크립트는 유지하지만 중복 CI 서비스를 운영하지 않습니다. [커밋 고정 CI](CI_REPRODUCIBILITY.md)를 참고합니다.
7. **완료 보고**: 결과, 실제 실행한 검증, 미검증/제약, 문서, 커밋 여부를 간단히 전달합니다. 커밋/푸시는 요청이 있을 때만 합니다.

이 루프는 AI가 지침을 반드시 읽는지까지 기술적으로 보장하지는 않습니다. AGENTS의 진입점과 CI 실패 피드백을 함께 사용하며, 사람의 설계·리뷰·승인을 대체하지 않습니다.

## 11. 규칙 변경과 예외

- 규칙이 요구를 막으면 먼저 이유·영향·대안·검증을 문서화하고 해당 가이드/게이트/테스트를 함께 수정합니다. 게이트 비활성화나 무시 옵션을 우회책으로 사용하지 않습니다.
- 보안/데이터 손실/추가 비용을 확대하는 예외는 사용자 확인이 필요합니다.
- 성능 상한과 API 계약은 변경 가능한 설계 값이지만, 근거 없이 현재 값을 변경하지 않습니다.

## 12. 기존 코드 점검과 후속 정리

이번 제정에서는 전체 소스의 패키지·설정·검증 흐름을 확인하고, 기존 코드에 바로 적용 가능한 자동 경계를 추가했습니다. 전체 메서드의 정적 분석·보안 감사·전면 리팩터링을 완료한 것은 아닙니다.

| 현재 상태 | 처리 방침 |
|---|---|
| JPA DTO/LAZY·OSIV off·읽기 트랜잭션·실제 SQL 테스트 | 유지. 게이트는 설정과 일부 import만, SQL 정확성은 통합 테스트로 확인 |
| 중앙 HTTP·취소·캐시 상한·동적 청크 | 유지. 위험 패턴은 게이트, 동작은 기존 Vitest/E2E로 확인 |
| 일부 Java/Vue의 압축 문장·wildcard import | 다음 해당 기능 수정 시 좁은 범위로 풀어 씀. 전체 포맷 재작성은 별도 작업 |
| ResourceHistoryController의 검증·존재 확인·페이지 조립·Repository 직접 호출 | 2026-10-17 ResourceHistoryService로 분리. Controller는 HTTP 바인딩·위임, Service는 페이지 검증·접근 확인·응답 조립. 기존 읽기 트랜잭션 경계 유지 |
| PrometheusOperations의 조회·변환·안전 제한 집중 | 전송은 기존 PrometheusClient, 유스케이스는 dashboard, 값/시계열 변환은 별도 메서드로 분리. 고정 허용 목록의 PromQL/URL 인코딩은 클래스 초기화 시 한 번 수행. 지표별 새 인터페이스/프레임워크는 추가하지 않음 |
| 포매터/정식 AST 아키텍처 검사 미도입 | 현재 EditorConfig·소규모 텍스트 게이트부터 시작. 필요와 오탐을 보고 별도 도입 결정 |
| Jenkins 원격 SCM/webhook·실제 탭 메모리 미확인 | 로컬 fixture 체크아웃 검증과 구분. 실제 실행 후 이력에 추가 |

개발 체계 도입과 이후 코드 정리의 결과는 [작업 이력](WORK_HISTORY.md)에 구분합니다. 코드 정리는 목적과 회귀 테스트를 가진 개별 작업으로 진행하며, 위 두 항목의 후속 정리는 WH-029에 기록합니다.
