# Keycloak 관리자 성능 검증

## 목적과 실행 조건

관리자가 Keycloak으로 실제 로그인하고 전체 10만 Pod를 조회할 때 기존 탐색 목표가 유지되는지 확인합니다. 토큰을 주입하거나 API 인증을 해제하지 않습니다. 실제 Authorization Code + PKCE S256, 서버 JWT 검증, ADMIN 권한과 PostgreSQL 조회를 거칩니다.

- 별도 인증 Compose의 NGINX 프로덕션 UI 5176·API 8083·Keycloak 8183을 사용합니다. 서버·DB·seed는 이미 준비된 상태이며 부팅 시간은 제외합니다.
- Chromium headless, 1440×1000, 브라우저 CPU 4x, HTTP 캐시 OFF, 네트워크 제한 없음입니다. 서버 CPU를 4배 제한한 부하 테스트가 아닙니다.
- 각 표본은 새 브라우저 context에서 비밀번호 로그인을 수행하고, 같은 context에서 SSO 쿠키를 사용한 재진입을 측정합니다. 반복 묶음마다 새 Chromium 프로세스를 실행합니다.
- 최초 로그인 표본도 보존하며 실패·목표 초과를 제거하지 않습니다. ID/비밀번호 입력 시간은 자동 입력 완료 후부터 측정하므로 사람의 입력 시간과 다릅니다.
- 매회 `/api/auth/me`의 ADMIN과 실제 summary 응답의 20 Cluster / 200 Node / 2,000 Namespace / 100,000 Pod를 검사하고 운영 메뉴 표시를 확인합니다. API 오류 응답도 검사합니다.

## 구간과 판정

| 구간 | 시작 → 종료 | 판정 |
|---|---|---|
| 비밀번호 로그인 | 자동 로그인 제출 → 화면 준비 | 별도 관측; 기존 비인증 500ms 목표와 혼합하지 않음 |
| SSO 재진입 | 앱 navigation → Keycloak 왕복·코드 교환·사용자 확인·화면 준비 | 500ms 목표 비교 |
| 최종 callback 문서 | 최종 문서 navigation 시작 → 화면 준비 | 보조 진단; 전체 SSO 시간으로 대체하지 않음 |
| 미캐시 펼침·캐시 펼침·접기 | 클릭 → 계층 DOM 반영 | 각각 100ms 이하 |
| 검색 | 250ms 디바운스 후 fetch 시작 → 실제 일치 문항 표시 | 300ms 이하 |
| 상태 필터 | change 이벤트 → ERROR 조건 목록 표시 | 200ms 이하 |
| 읽기 전용 수동 갱신 | 클릭 → 실제 요청 그룹 완료·목록 준비 | 200ms 이하 |

화면 준비는 Cluster 루트·Pod 첫 목록·실제 10만 건 집계·관리자 표시가 준비된 뒤 두 번의 requestAnimationFrame까지입니다. skeleton 표시만으로 완료하지 않습니다. 로그인/SSO 전체 시간은 Node 측 경과 시간으로 자동화 호출·대기 관측의 작은 오버헤드도 포함합니다. callback 및 탐색 구간은 브라우저 performance 시계로 측정합니다.

수동 갱신은 목록·건수·펼친 계층의 실제 인증 GET 완료를 확인하지만 DB 값을 직접 변경하지 않습니다. 기존 갱신 측정의 **변경값 전파**와는 별도 시나리오입니다. 이 검증만으로 5페이지 갱신·자동 폴링·합성 FPS·탭 메모리까지 재통과했다고 주장하지 않습니다.

API 보조 시간은 브라우저 request부터 requestfinished까지이며 대기·네트워크·본문 수신이 포함됩니다. 순수 SQL 실행 시간이나 JWT 검증 시간으로 해석하지 않습니다. 기존 호스트 preview와 새 인증 NGINX는 제공 경로도 달라 비인증 과거 표본과의 차이 전체를 인증 오버헤드라고 계산할 수 없습니다.

## 재현·비밀값 보호

프로젝트 루트에서 인증 환경을 준비한 뒤 실행합니다. 기존 비밀값과 DB 볼륨은 유지합니다.

```bash
python3 scripts/auth-local.py
python3 scripts/test-auth.py
PERF_LABEL=auth-admin-local PERF_REPETITIONS=20 python3 scripts/test-auth.py --performance
# 같은 명령: frontend 디렉터리에서 npm run test:performance:auth
```

`PERF_REPETITIONS`는 3~50, label은 80자 이하 영문 소문자·숫자·하이픈만 허용합니다. 원본은 Git 제외 `frontend/.validation/performance/<label>.json`에 0600으로 저장하며 기존 파일을 덮어쓰지 않으므로 새 label을 지정합니다. 반복 수 부족·검증 오류·목표 초과가 있으면 성능 명령은 실패 코드로 종료합니다. 첫 묶음은 SSO 전체 시간에 목표 필드를 추가하기 전 실행했지만 원본 20개 값이 전부 500ms 미만인지 확인하며 원본을 덮어쓰지 않습니다.

전용 runner는 로컬 비밀번호와 JWT/인증 코드 등을 마스킹합니다. 측정 스크립트는 오류 message/call log를 저장하지 않고 고정 단계·오류 분류만 기록합니다. 비밀번호·토큰·인증 URL query·헤더·응답 본문·storageState·trace·HAR·스크린샷은 결과에 저장하지 않습니다. API는 고정 endpoint 분류와 시간만 기록하고 실제 계정 비밀번호는 기존 Git 제외 파일에서 읽습니다. 새 외부 OSS·AI·클라우드 API나 메일 발송은 없습니다.

## 제한과 후속 검증

- 관리자 단일 사용자·로컬 인증 환경의 결과입니다. A/B 범위 조회 성능, 동시 접속, 공개 네트워크, 서버 부팅, 최초 JWKS 검색과 토큰 갱신 경계는 별도 검증입니다.
- 이미 기동된 Keycloak의 캐시 상태를 초기화하지 않았습니다. 매회 새 로그인은 새 브라우저/SSO 세션을 뜻하며 새 서버/DB를 뜻하지 않습니다.
- 실제 Chrome 작업관리자 탭 메모리는 미검증입니다. 기능 E2E 5개와 성능 표본은 서로 다른 검증입니다.
- 서비스 코드·스키마·보안 정책은 이번 측정에서 변경하지 않았습니다. 전체 Gradle/Jenkins 재실행 대신 실제 인증 회귀·도구 문법·빠른 게이트를 실행합니다.
