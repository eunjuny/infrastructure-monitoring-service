# 구현 계획과 설계

## 기준

과제 가이드의 기능·성능 조건을 우선하고, 공고의 Java 17+, Spring Boot 3.x, JPA, RDBMS, 테스트 경험과 연결합니다. 이전 프로젝트 구조를 복사하지 않습니다.

과제의 Cluster → Node → Namespace → Pod는 탐색용 모델이며 실제 Kubernetes 객체 관계와 다릅니다.

## 요구사항과 진행 상태

| 계층 탐색 | 부모별 API, 펼칠 때 지연 로딩 | API 작성, 화면 및 실제 DB 검증 예정 |

## 계층 데이터 모델링

독립된 4개 테이블과 외래키로 관계를 표현합니다. 이름·상태·updated_at을 공통으로 보관하며 상위 계층 전체를 Entity 그래프로 직렬화하지 않습니다. 부모 내 이름 유일성을 DB에서 검증합니다. 현재 건수 API의 count 집계는 명시적 요청용이며 빈번한 폴링 대상으로 삼지 않습니다.

## 인덱스와 쿼리 전략

V1은 부모별 이름 유일성과 (부모 ID, 상태, ID), Pod의 (상태, ID) 인덱스를 구성합니다. V2는 상태 조건이 없을 때의 (부모 ID, ID), 나머지 유형의 (상태, ID), 부분 문자열 검색용 pg_trgm GIN 인덱스를 추가합니다. 각 쿼리는 limit + 1개만 반환하며 전체 검색은 각 유형의 후보를 제한한 뒤 depth·ID로 병합합니다. 실제 SQL과 EXPLAIN (ANALYZE, BUFFERS) 검증은 DB 접근 허용 후 진행합니다. 짧거나 흔한 검색어에 대한 GIN 효과를 보장하지 않습니다.

## API 설계

건수 API 외에 유형별 목록, 하위 목록, 상세, 검색, 경로 API를 작성했습니다. [API 계약](API.md)을 참고합니다. ID 기반 keyset 커서를 사용하고 응답은 최대 100개로 제한합니다. 전체 검색은 depth·ID 순서입니다. 이름·상태·부모 조건은 AND로 처리하고 검색 결과는 상위 경로를 함께 반환합니다. 임의 페이지 점프나 데이터 스냅샷 일관성은 제공하지 않습니다. 화면 단계에서 순차 탐색, 프리페치와 제한된 캐시를 연결하며 필터 변경 시 커서를 초기화합니다.

## 프론트엔드 렌더링 전략

초기 진입에는 Cluster만 조회하고, 하위 계층은 필요한 시점에 로드합니다. 탐색 트리는 펼친 항목만 평탄화하며 긴 목록은 TanStack Virtual을 사용합니다. 가상화만으로 네트워크·메모리가 제한되는 것은 아니므로 서버 페이지와 클라이언트 캐시 상한을 함께 적용합니다. 상태 변경 시 ID 기반으로 기존 행과 병합하고 전체 목록을 비우거나 재마운트하지 않습니다.

## 검증 및 제외 범위

요청·커서·서비스·MVC·SQL 바인딩 단위 테스트 40개를 캐시 환경에서 실행해 통과했습니다. 스키마·10만 Pod·재적재 검증 1개와 실제 검색·페이지·경로·오류 API 통합 테스트 12개는 Testcontainers PostgreSQL 17로 작성했으나 실행하지 못했습니다. Vitest/Playwright로 화면 흐름을 검증할 계획입니다. 실제 Kubernetes, Keycloak, Redis, Kafka, Elasticsearch, MSA는 필수 요구 해결의 근거가 없어 초기 범위에서 제외했습니다. [1단계 보고서](VALIDATION_REPORT.md), [2단계 보고서](STAGE2_REPORT.md)를 참고합니다.
