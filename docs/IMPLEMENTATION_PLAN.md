# 구현 계획과 설계

## 기준

과제 가이드의 기능·성능 조건을 우선하고, 공고의 Java 17+, Spring Boot 3.x, JPA, RDBMS, 테스트 경험과 연결합니다. 이전 프로젝트 구조를 복사하지 않습니다.

과제의 Cluster → Node → Namespace → Pod는 탐색용 모델이며 실제 Kubernetes 객체 관계와 다릅니다.

## 계층 데이터 모델링

독립된 4개 테이블과 외래키로 관계를 표현합니다. 이름·상태·updated_at을 공통으로 보관하며 상위 계층 전체를 Entity 그래프로 직렬화하지 않습니다. 부모 내 이름 유일성을 DB에서 검증합니다. 현재 건수 API의 count 집계는 명시적 요청용이며 빈번한 폴링 대상으로 삼지 않습니다.

## 인덱스와 쿼리 전략

V1은 부모별 이름 유일성과 (부모 ID, 상태, ID), Pod의 (상태, ID) 인덱스를 구성합니다. V2는 조건 없는 (부모 ID, ID), 나머지 유형의 (상태, ID), pg_trgm GIN 인덱스를 추가합니다. 각 쿼리는 limit + 1개만 반환하고 전체 검색은 유형별 후보를 depth·ID로 병합합니다. EXPLAIN (ANALYZE, BUFFERS)에서 선택적인 이름 검색은 GIN, 상태·ID 커서 조회는 인덱스를 사용하는 것을 확인했습니다. 한 글자 미일치 검색은 순차 스캔을 사용했으며 짧거나 흔한 검색어의 GIN 효과를 보장하지 않습니다. [실행 계획과 브라우저 측정](PERFORMANCE_RESULTS.md)을 참고합니다.

## API 설계

건수 API 외에 유형별 목록, 하위 목록, 상세, 검색, 경로 API를 작성했습니다. [API 계약](API.md)을 참고합니다. ID 기반 keyset 커서를 사용하고 응답은 최대 100개로 제한합니다. 전체 검색은 depth·ID 순서입니다. 이름·상태·부모 조건은 AND로 처리하고 검색 결과는 상위 경로를 함께 반환합니다. 임의 페이지 점프나 데이터 스냅샷 일관성은 제공하지 않습니다. 화면 단계에서 순차 탐색, 프리페치와 제한된 캐시를 연결하며 필터 변경 시 커서를 초기화합니다.

## 프론트엔드 렌더링 전략

초기 진입에는 Cluster 첫 페이지, 전체 Pod 첫 페이지와 건수를 조회합니다. 하위 계층은 필요할 때 로드하고 펼친 항목만 평탄화합니다. 고정 높이 가상 리스트는 뷰포트·오버스캔만 표시합니다. 목록 최대 5페이지·500개, 계층 최대 24페이지를 보관합니다. 수동·자동 갱신은 창을 원자적으로 교체하되 같은 키와 변경 없는 행 객체·선택·스크롤을 유지합니다. 숨김·오프라인에서는 폴링을 중지합니다. [화면 설계](FRONTEND_RENDERING.md), [자동 갱신](LIVE_UPDATES.md)을 참고합니다.

## 검증 및 제외 범위

정식 Maven 테스트 69개(실제 PostgreSQL 통합 17개 포함), Vitest 56개, 실제 API Chromium E2E 7개가 통과했습니다. [후속 검증 보고서](STAGE4_REPORT.md), [UI 검증](UI_DESIGN.md), [성능·안정성 보강](PERFORMANCE_RESULTS.md)에 근거를 기록했습니다. 이전 제한 기록은 [1단계](VALIDATION_REPORT.md), [2단계](STAGE2_REPORT.md), [3단계](STAGE3_REPORT.md)에 유지합니다. 실제 Kubernetes, Keycloak, Redis, Kafka, Elasticsearch, MSA는 필수 요구 해결의 근거가 없어 제외했습니다.
