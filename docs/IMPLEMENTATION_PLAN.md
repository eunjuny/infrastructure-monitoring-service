# 구현 계획과 설계

## 기준

과제 가이드의 기능·성능 조건을 우선하고, 공고의 Java 17+, Spring Boot 3.x, JPA, RDBMS, 테스트 경험과 연결합니다. 이전 프로젝트 구조를 복사하지 않습니다.

과제의 Cluster → Node → Namespace → Pod는 탐색용 모델이며 실제 Kubernetes 객체 관계와 다릅니다.

## 계층 데이터 모델링

독립된 4개 테이블과 외래키로 관계를 표현합니다. 이름·상태·updated_at을 공통으로 보관하며 상위 계층 전체를 Entity 그래프로 직렬화하지 않습니다. 부모 내 이름 유일성을 DB에서 검증합니다. 현재 건수 API의 count 집계는 명시적 요청용이며 빈번한 폴링 대상으로 삼지 않습니다.

## 인덱스와 쿼리 전략

부모별 이름 유일성 인덱스와 (부모 ID, 상태, ID) 복합 인덱스를 구성했습니다. Pod 전체 상태별 탐색에는 (상태, ID)를 사용합니다. 부모별 정렬, 페이지 방식과 검색 인덱스는 실제 SQL과 EXPLAIN (ANALYZE, BUFFERS)로 검증하며 필요에 맞춰 마이그레이션으로 추가합니다. 부분 문자열 검색 시 pg_trgm을 검토하되 현재 초기 스키마에는 도입하지 않았습니다.

## API 설계

구현됨: GET /api/resources/summary, GET /actuator/health.

예정: 유형별 하위 목록, 단일 상세, 검색, 경로 조회 API. 페이지 크기 상한을 적용하며 정렬의 마지막 조건에는 유일 ID를 포함합니다. 검색과 필터는 AND 조건으로 정의하고, 빠른 검색 입력에서는 오래된 응답을 무시하거나 취소합니다. 경로 이동과 가상 리스트의 임의 위치 탐색을 고려해 페이지 방식은 별도로 확정합니다.

## 프론트엔드 렌더링 전략

초기 진입에는 Cluster만 조회하고, 하위 계층은 필요한 시점에 로드합니다. 탐색 트리는 펼친 항목만 평탄화하며 긴 목록은 TanStack Virtual을 사용합니다. 가상화만으로 네트워크·메모리가 제한되는 것은 아니므로 서버 페이지와 클라이언트 캐시 상한을 함께 적용합니다. 상태 변경 시 ID 기반으로 기존 행과 병합하고 전체 목록을 비우거나 재마운트하지 않습니다.

## 검증 및 제외 범위

JUnit/Testcontainers로 실제 PostgreSQL 스키마·조회·검색·경로를 검증하고, Vitest/Playwright로 UI 상태와 전체 사용 흐름을 검증할 계획입니다. 현재 테스트는 스키마 생성 확인만 작성되어 있습니다. 실제 Kubernetes, Keycloak, Redis, Kafka, Elasticsearch, MSA는 필수 요구 해결의 근거가 없어 초기 범위에서 제외했습니다.
