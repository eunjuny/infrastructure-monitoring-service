# Pod 15만 개 확장

적용일: 2026-10-17 · 현재 기본 규모: Cluster 20 / Node 200 / Namespace 2,000 / Pod 150,000

**아래는 WH-031의 최초 균등 확장·당시 성능 기록입니다.** 이후 WH-035에서 추가 5만 fixture의 부모만 앞쪽 Namespace로 재배치하고 user1 100,000/user2 50,000으로 변경했습니다. 현재 seed/분포/계정/이행은 [후속 설계](USER_SCOPES_AND_LOGIN_THEME.md)를 기준으로 하며, 아래 균등 분포의 원본 성능 수치를 새 분포 측정으로 바꾸지 않습니다.

## 확장과 보존 정책

`scripts/seed.sql`은 기존 100,000개를 삭제하거나 재배치하지 않습니다. 원래 ID 1~100000은 기존 Namespace 공식 `((id-1)/50)+1`을 유지하고, 신규 ID 100001~150000은 `((id-100001)/25)+1`로 Namespace마다 25개씩 추가합니다. 결과적으로 Namespace마다 75개, Cluster마다 7,500개이며 VIEWER A/B는 각각 75,000개를 조회합니다.

`ON CONFLICT (id) DO NOTHING`이 기존 이름·상태·갱신 시각·재시작 횟수를 덮어쓰지 않도록 합니다. 스키마는 같으므로 Flyway V1~V3를 수정하거나 새 마이그레이션을 추가하지 않습니다. 이미 15만 개를 적재한 환경에서 다시 실행해도 같은 행을 중복 생성하지 않습니다.

로컬 개발·전체 Compose·인증 앱 DB 세 곳에 각각 적용했고, 각 환경에서 기존 10만 행의 ID·이름·부모 관계 digest가 같고 Namespace별 최소/최대 건수가 모두 75임을 확인했습니다. 앱 DB만 대상으로 삼았으며 Keycloak identity DB와 다른 프로젝트 DB는 건드리지 않았습니다. 실행 중인 Mock의 정상적인 상태 변경은 계속 허용합니다.

조회 최대 100개·캐시 500개·가상 리스트·Mock 배치 최대 116행은 그대로입니다. 권한은 ID 구간이 아니라 Cluster 관계에 적용하므로 추가된 ID 100001은 A, 125001은 B의 조회 범위입니다.

## 실행

### 생성 배치와 서비스 조회는 분리됩니다

`scripts/seed.sql`은 **데이터 준비용 SQL 배치**입니다. PostgreSQL의 `generate_series`로 계층별 Mock 행을 만들고 `INSERT ... ON CONFLICT DO NOTHING`으로 DB에 넣습니다. 기존 설치에 재실행할 때 기존 리소스 값을 전부 덮거나 삭제하지 않으며, 과거 seed 규칙으로 추가됐던 식별 가능한 신규 Pod의 부모 배치만 보정합니다. 이 스크립트는 화면/API 요청 때 실행되지 않습니다.

실제 서비스의 저장소는 같은 실행 모드의 PostgreSQL입니다. Spring Boot는 요청마다 전체 15만 행을 메모리에 올리거나 스크립트를 다시 돌리지 않고, JPA 조회에 부모·상태·ID 인덱스와 keyset 페이지 조건을 사용해 필요한 범위/페이지를 읽습니다. 인증·runtime·호스트 개발은 각자의 앱 DB를 가지므로 seed 실행도 목표 DB를 지정해야 합니다. 인증의 `identity` DB에는 적재하지 않습니다. 예외적으로 Mock 상태 시뮬레이터는 기존 요구사항에 따라 제한된 DB 행과 이력을 변경합니다. 이는 seed와 별도 런타임 기능입니다.

Flyway 마이그레이션이 끝난 호스트 개발 DB:

```bash
docker compose exec -T db psql -U monitoring -d monitoring -v ON_ERROR_STOP=1 < scripts/seed.sql
```

전체 Compose의 기존 seed 서비스가 이미 완료된 경우:

```bash
docker compose -f compose.runtime.yaml run --rm --no-deps seed
```

인증 모드는 `scripts/auth-local.py`로 해당 환경을 준비한 뒤 같은 seed를 그 환경의 **앱 DB**에 적용합니다. 인증 환경 비밀값을 출력하거나 identity DB에 적재하지 않습니다. 환경별 DB가 다르므로 하나에 적용해도 나머지에 자동 전파되지 않습니다. 화면의 전체 건수는 정기 폴링에서 집계하지 않으므로 수동 새로고침 또는 페이지 재진입으로 확인합니다.

## 기능 검증

- Gradle 서버 120개 통과(실제 PostgreSQL 49개 포함), 실패·오류·skip 0.
- 기존 10만 설치를 테스트 DB에서 재현한 뒤 확장해 원래 상태·갱신 시각·이름·부모·재시작 수 보존, 재실행과 15만 건수·균등 분포를 검사했습니다.
- Namespace 2000의 기존 50개 다음 페이지에서 새 25개를 조회하고, `api-pod-150000` 검색의 경로를 검사했습니다.
- 기존 Cluster 권한과 추가 ID의 A/B 허용·교차 404·이력 차단을 검사했습니다.
- Vitest 77개·타입 검사·프로덕션 빌드 통과. 실제 Keycloak 5개에서 ADMIN 150,000·VIEWER 각 75,000을 확인했습니다.
- 새 프로덕션 preview를 현재 호스트 API에 연결해 읽기 전용 브라우저 10개를 통과했습니다. 기존 데이터를 직접 변경하는 자동 갱신 E2E 한 항목은 이번 실행에서 제외했으며 전체 11개 통과라고 하지 않습니다.

첫 기본 E2E는 기존 전체 Compose의 이전 이미지에서 실행되어 9개 통과·운영 경보 1개 실패였습니다. 확인 결과 해당 backend의 alerts API는 404, Prometheus rules는 빈 목록이었습니다. 별도 인증 실행과 기본 실행의 출력 경로가 겹쳐 artifact ENOENT도 발생했습니다. 현재 호스트의 경보 API/세 규칙을 확인하고 별도 output 경로·순차 실행으로 재검증했습니다. 데이터 확장 실패나 테스트 기준 완화로 처리하지 않았으며 기존 이미지를 임의 재배포하지 않았습니다.

## 집중 성능 검증

별도 tmpfs PostgreSQL에 15만 Pod와 이력 500개를 만들고 이전 안정화/현재 JAR 두 개를 동일 데이터에 연결했습니다. API 7종을 단일·동시성 상한 8에서 버전별 100회씩 총 **2,800건**, HTTP 상태·본문 검증 오류 0으로 완료했습니다. 목록·신규 ID 이름 검색·미일치 단문 검색·이력 3종·실제 Prometheus를 포함합니다.

현재 JAR의 단일 요청 P95는 목록 11.42ms, 신규 ID 검색 127.03ms, 미일치 단문 검색 89.44ms입니다. 서버 API 지연을 브라우저 검색 목표 300ms 통과와 동일하게 해석하지 않습니다. 동시성 8의 운영 지표 P95는 이전 JAR 127.14ms·현재 444.91ms로 증가했습니다. 외부 Prometheus·호스트 부하·JIT 등의 영향은 원인을 확정하지 않았으며 모든 지표가 빨라졌거나 안정적으로 동일하다고 주장하지 않습니다.

화면은 같은 프로덕션 dist·동일 프록시·Chromium·CPU4x·캐시OFF·1440×1000에서 버전별 20회 교대로 측정했습니다. 현재 초기 진입 중앙값 260.2ms·P95 305.1ms·최대 324.2ms, **500ms 초과 0/20**이며 화면 측정 오류는 0입니다. 이력/운영 카드 표시 P95는 94.5/113.9ms입니다. 서버/DB는 준비된 상태이고 실제 Cluster 루트·Pod 목록·150,000 건수와 두 번의 RAF를 완료 조건으로 사용합니다.

측정 준비 중 기존 Gradle 통합 테스트가 마무리됐습니다. 원본의 전체 컨테이너 ID 보존 검사는 false였지만, 빠진 두 개가 해당 테스트의 Ryuk와 PostgreSQL임을 JUnit 로그의 시작 ID로 확인했습니다. 비교 실행이 이들을 종료한 것이 아니며 기존 Compose 앱 컨테이너는 모두 유지됐습니다. 원본 false를 숨기거나 true로 덮지 않고 별도 설명·검사 결과를 남깁니다.

[전체 측정 표본·환경·중간 실패·JAR 해시·정리 결과](performance/2026-10-17-scale-150k.json)를 보관합니다. 측정용 JVM·프록시·tmpfs DB·추가 preview는 종료/정리했고 기존 DB/서비스는 유지합니다. 이전 10만 성능 기록과 비교해 데이터 증가만의 영향을 분리한 실험은 아닙니다. 실제 Keycloak의 성능, 스크롤 FPS·작업관리자 메모리·원문 전체 성능 목표·새 Jenkins/이미지/복구 파이프라인은 이번에 재측정하지 않았습니다.
