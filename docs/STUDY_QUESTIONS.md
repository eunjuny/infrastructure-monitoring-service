## 1. Mock 시뮬레이터

실제 Kubernetes 없이도 상태 변화·화면 갱신·이력·관측을 확인하도록, 백엔드가 DB의 Mock 리소스를 제한된 양만큼 변경하는 기능입니다. 실제 서버나 Pod를 만들지 않고 Mac의 CPU를 Node 사용률로 읽지도 않습니다.

기본 설정에서는 꺼져 있고 `mock` 프로필에서 켭니다. 현재 호스트 실행 스크립트와 전체 Compose는 Mock 프로필을 사용합니다. 시작 후 기본 10초 뒤 첫 배치를 실행하고, 배치가 끝나면 기본 5초 뒤 다음 묶음을 실행합니다. ID 순으로 진행하다 끝에 도달하면 처음으로 돌아옵니다.

| 유형 | 배치당 최대 | 변경할 값 |
|---|---:|---|
| Cluster | 1개 | 상태·갱신 시각 |
| Node | 5개 | 상태·갱신 시각·CPU/메모리 사용률 |
| Namespace | 10개 | 상태·갱신 시각 |
| Pod | 100개 | 상태·갱신 시각, WARNING→ERROR일 때 재시작 횟수 증가 |

상태는 NORMAL→WARNING→ERROR→NORMAL로 순환합니다. Node CPU는 7, 메모리는 11씩 더하고 0~100 범위에서 순환하므로 실제 부하를 측정한 값이 아닌 결정적인 데모 수치입니다. 예를 들어 CPU 30%였다면 해당 Node의 다음 변경에서 37%가 됩니다.

**전체 15만 Pod가 5초마다 바뀌는 것은 아닙니다.** 한 번에 최대 100개이므로 동일 Pod를 다시 변경하기까지 순환이 필요합니다. Pod 150,000개 기준 배치 처리 시간을 제외해도 한 순환은 대략 125분입니다. 보고 있는 Pod가 오래 그대로여도 스케줄러 정지라고 단정할 수 없습니다.

DB 변경과 화면 갱신도 별개입니다. 서버 시뮬레이터가 값을 바꾸고 브라우저가 현재 목록·펼친 계층·선택 상세를 재조회합니다. 화면 자동 갱신을 꺼도 서버 Mock 작업은 계속될 수 있습니다. 숨김·오프라인 역시 화면 폴링을 멈추는 것이지 서버 스케줄러를 끄지는 않습니다.

한 배치의 변경과 이력은 함께 커밋합니다. 실패하면 배치를 롤백하고 다음 주기에 다시 시도합니다. 자세한 구현은 [Mock·폴링 설계](LIVE_UPDATES.md)를 참고합니다.

## 2. 운영 카드와 추이 차트

리소스 목록의 Node CPU·Pod 상태는 **가상 인프라 데이터**이고, 운영 관측은 실행 중인 **Spring Boot 서비스의 실제 계측값**입니다. 시뮬레이션을 실행하는 코드의 처리 시간·변경량·실패 횟수 역시 실제 실행을 측정합니다.

| 카드 | 의미·읽는 방법 |
|---|---|
| 수집 대상 상태 | `up=1`은 **수집 성공**, `up=0`은 **수집 실패**로 표시. 누락/비유한 값은 **표본 없음**, 예상 밖의 유한 값은 **확인 불가**. 모든 기능의 정상을 보장하지는 않음 |
| 리소스 API 요청 추정 / 5분 | 최근 5분 목록·검색·상세 등 리소스 API 요청 증가량. 자동 폴링도 포함하므로 사용자/클릭 수와 다름 |
| API P95 / 5분 | 최근 5분 리소스 API 서버 처리 지연의 근사 95백분위. 브라우저 렌더링 시간은 제외 |
| DB 조회 P95 / 5분 | 목록·검색 Repository 구간의 근사 95백분위. 쿼리 구성·SQL 왕복·DTO 조립 포함, 순수 PostgreSQL 내부 실행 시간이나 모든 SQL 지연은 아님 |
| API 5xx / 5분 | 최근 5분 리소스 API 서버 오류 증가량. Mock Pod의 ERROR 상태나 400/404가 아님 |
| JVM heap 사용 | 백엔드 Java 객체 저장에 쓰는 heap. Mac 전체·브라우저·DB 메모리 또는 JVM 전체 RSS와 다름 |
| DB 사용 중 연결 | HikariCP에서 현재 빌려준 연결 수. 전체 풀 크기나 DB 전체 연결 수와 다름 |
| Mock 변경 행 추정 / 5분 | 최근 5분 커밋에 성공한 네 유형의 변경량. 같은 행을 두 번 바꾸면 두 번 집계 |
| Mock 실패 / 5분 | DB 오류 등으로 배치가 실패한 횟수. Pod 상태를 의도적으로 ERROR로 바꾼 것은 배치 실패가 아님 |
| Mock 배치 P95 / 5분 | 제한된 배치의 트랜잭션 처리 시간의 근사 95백분위. 다음 배치까지 기다리는 5초는 제외 |

P95는 평균이 아닙니다. P95가 100ms라면 대략 요청 95%가 100ms 이내이고 나머지는 더 느릴 수 있다는 뜻입니다. 현재는 Histogram 버킷으로 근사 계산합니다. Counter의 `increase(...[5m])`는 수집 경계에서 추정하므로 소수로 표시될 수 있습니다.

표본 부족·NaN은 `표본 없음`, 연결 장애는 오류로 구분합니다. 실제 요청 표본이 있고 5xx 시계열만 없을 때의 0과 Prometheus 자체가 응답하지 않는 상황을 혼동하지 않습니다.

### 추이 차트 2개

- API P95: 최근 30분 API 처리 지연의 변화입니다.
- DB 조회 P95: 같은 기간 목록·검색 조회 구간 지연의 변화입니다.
- 가로축은 시간, 세로축은 ms입니다. 약 1분 간격의 각 점은 해당 시점 직전 5분의 P95이며 단일 요청이나 누적 평균이 아닙니다.
- 두 차트가 함께 상승하면 DB 조회가 API 지연에 영향을 주는지 살펴보고, API만 상승하면 다른 처리도 점검합니다. 두 지표만으로 원인을 확정할 수는 없습니다.
- 표본이 없는 구간을 정상 0으로 연결하지 않습니다. DB Timer가 상세/범위 검증 등 모든 SQL을 포함하지 않는 것도 고려해야 합니다.

원본 정의·안전 제한은 [운영 관측 설계](OPERATIONS_AND_DELIVERY.md#3-prometheus-운영-관측), 다음 질문의 실행 모드는 [README](../README.md)를 참고합니다.

### 추가 질문: 실제 운영에서도 DB에서 지표를 가져오나요?

두 경로를 구분합니다.

```text
리소스 데이터: Vue → 리소스 API → PostgreSQL의 Node·Pod 등 행
서비스 지표: HTTP/JVM/연결 풀/조회 계측 → Actuator → Prometheus 수집·시계열 저장
            → 서버의 고정 PromQL → 운영 화면
```

Prometheus가 `/actuator/prometheus`를 HTTP로 읽는 것이 **수집(scrape)**입니다. HTTP 처리 시간은 요청 계측, heap은 JVM 런타임, 활성 연결은 HikariCP 연결 풀, 조회 시간은 Repository 호출 계측에서 나옵니다. 이 카드들을 만들기 위해 Prometheus가 리소스 테이블을 직접 조회하지는 않습니다. 실제 Kubernetes를 연동한다면 리소스 자체의 출처는 Kubernetes API/수집기 등이 될 수 있지만 이 과제에서는 아직 연동하지 않았습니다.

수집 성공은 지표 응답을 읽었다는 뜻이지, 모든 API·DB·업무 처리가 정상이라는 보장은 아닙니다. Prometheus 자체 조회 장애는 카드의 수집 실패와 달리 소스 연결 오류로 표시합니다. PostgreSQL 내부 쿼리/잠금/전체 세션을 상세 수집하는 DB exporter는 현재 구현하지 않았습니다.

### 추가 질문: P95는 예외적인 상황을 제외하나요?

아닙니다. **오류나 느린 요청을 삭제하는 규칙이 아니라 응답 시간 분포를 읽는 위치**입니다. 100건 중 약 95건이 100ms 이내여도 나머지 5건은 1초 이상 걸릴 수 있습니다. 그 느린 요청들도 원본 계측에는 포함되며 P95 하나로는 얼마나 느렸는지 알 수 없습니다. 현재 API 조회식은 HTTP 상태로 성공 요청만 골라내지 않습니다.

현재 P95는 Histogram 버킷을 이용한 근사값입니다. 꼬리 지연은 P99·최댓값, 오류는 실패율/5xx, 표본 충분성은 요청 수와 함께 봐야 합니다. 이는 읽는 방법이며 해당 보조 차트가 모두 구현됐다는 뜻은 아닙니다. 목표가 모든 표본 500ms 이내라면 P95 통과만으로 충분하지 않고 최댓값·초과 건수도 확인해야 합니다.

### 추가 질문: JVM heap과 DB 사용 중 연결도 관리해야 하나요?

**JVM heap**은 Java 객체가 사용하는 메모리입니다. 증가했다가 GC(사용하지 않는 객체 회수) 후 감소하는 것은 정상일 수 있습니다. 지속적인 증가·GC 후에도 남는 메모리·긴 GC 정지는 응답 지연과 메모리 부족 종료의 단서라 운영자가 확인할 가치가 있습니다. 사용량만으로 누수를 확정할 수 없고 최대 heap 대비 비율·GC·부하를 함께 봐야 합니다. 현재 카드는 사용량만 표시하며 JVM 전체 RSS나 Mac 메모리가 아닙니다.

**DB 사용 중 연결**은 HikariCP가 애플리케이션에 빌려준 연결 수입니다. 예를 들어 최대 10개인 풀에서 두 요청이 각각 하나씩 사용하면 활성 연결은 2개입니다. DB 작업이 끝나면 풀에 반환해 재사용합니다. 접속 사용자 수나 PostgreSQL 서버의 전체 연결 수가 아닙니다. 0개는 유휴 상태일 수 있고, 최대치에 가까운 값이 지속되면서 대기/시간 초과가 생기면 느린 쿼리·긴 트랜잭션·연결 반환 누락 등을 점검합니다. 무조건 풀을 키우는 것은 DB 부하를 늘릴 수 있습니다.

## 3. 실행 모드를 어떻게 선택하나요?

현재는 **호스트 개발 / 전체 컨테이너 / 인증 검증**의 세 구성이 있습니다. 공개 서비스용 운영 배포가 완성되어 dev/prod 스위치만 바꾸는 구조는 아닙니다.

| 목적 | 실행 구성 | 화면·API | 특징 |
|---|---|---|---|
| 코드를 수정하며 개발 | 호스트 Java·Vite, DB 등은 Compose | 5174 / 8081 | 코드 변경 확인에 적합, 기본 로그인 없음 |
| 이미지로 전체 실행 확인 | `compose.runtime.yaml` | 5175 / 8082 | NGINX 정적 화면·백엔드·별도 DB, Mock 활성 |
| 로그인·조회 범위 확인 | `compose.auth.yaml`과 실행 스크립트 | 5176 / 8083 | Keycloak·관리자/A/B, 별도 앱/인증 DB |

프로젝트 루트에서 실행합니다. 아래는 선택지이며 전부 동시에 실행할 필요는 없습니다.

```bash
# 호스트 개발: DB → 백엔드
docker compose up -d db
./backend/gradlew -p backend bootRun
# Flyway 테이블 생성 후 별도 터미널
docker compose exec -T db psql -U monitoring -d monitoring -v ON_ERROR_STOP=1 < scripts/seed.sql
(cd frontend && npm ci && npm run dev)

# 호스트에서 상태 변경도 필요하면 기본 백엔드 대신 실행
./backend/gradlew -p backend bootRun --args='--spring.profiles.active=mock'

# 호스트 개발의 지표·경보 수집
docker compose --profile monitoring up -d --build db prometheus alertmanager alert-receiver

# 전체 컨테이너 실행
docker compose -f compose.runtime.yaml --profile monitoring up -d --build

# 선택형 인증 환경
python3 scripts/auth-local.py
```

같은 8081 포트의 백엔드를 중복 실행하지 않습니다. `mock`은 가상 데이터 변경을 켜는 Spring 프로필이고 `monitoring`은 관측 컨테이너를 켜는 Compose 프로필입니다. 인증 구성은 별도 Compose와 프론트 빌드 설정을 사용하며 화면 파라미터만 바꿔 켜지지 않습니다. 세 환경의 DB는 독립적이므로 변경도 공유하지 않습니다.

인증 환경도 로컬 HTTP/Keycloak 개발 실행입니다. 공개 운영에는 HTTPS·공개 issuer/redirect·시크릿 관리·접근 제한·백업 등을 별도로 설계해야 합니다. 기존 runtime 이미지가 오래됐다면 소스 수정만으로 반영되지 않으므로 `--build`로 다시 빌드해야 합니다. 준비 조건과 자격 정보 보관은 [README](../README.md), [인증 문서](AUTHENTICATION.md)를 참고합니다.

## 4. 기술 선택 근거는 충분한가요?

필수 과제는 스택을 제한하지 않습니다. 핵심은 대용량 계층 조회·렌더링·갱신이며 인증/CI/관측은 공고와 운영 검증을 고려한 선택형 확장입니다. 모든 기술이 유일한 정답이거나 성능이 가장 좋다는 주장은 하지 않습니다.

| 기술 | 이 서비스에서 해결하는 문제·선택 근거 | 대안·주의점 |
|---|---|---|
| Java 21·Spring Boot 3 | 공고 Java17+/Boot3 조건, REST·검증·트랜잭션·보안·계측 통합 | 다른 서버 기술도 과제 수행 가능. 프레임워크만으로 성능 보장 안 됨 |
| JPA/Hibernate | 계층 관계 매핑과 DTO 조회, 공고 ORM 경험 요구 | JDBC도 타당. JPA가 본질적으로 더 빠른 것은 아님. LAZY·OSIV off·keyset·SQL 횟수 검증 필요 |
| PostgreSQL·pg_trgm | 실제 15만 행 저장, FK/트랜잭션, 부모/상태 인덱스·부분 이름 검색 | MySQL도 가능. 모든 검색어가 GIN을 쓰지는 않음 |
| Flyway | 스키마 변경 순서와 환경 간 재현성 | 자동 스키마 변경 대신 명시적 마이그레이션/validate |
| HikariCP | 연결 재사용·동시 DB 접근 자원 관리·대기 제한 | 풀 증설이 느린 SQL 해결책은 아님 |
| Gradle Wrapper·Kotlin DSL | 사용자 요청에 따른 통일, 빌드 버전/체크섬/의존성 잠금·CI 재현성 | Maven도 타당. 전환에서 빌드 속도 개선은 측정하지 않음 |
| Vue 3·TypeScript·Vite | 계층/선택/검색 상태, API 타입, 개발 피드백·정적 번들 | React도 가능. Vite 개발 서버는 공개 운영 서버가 아님 |
| 자체 가상 리스트·제한 캐시 | 고정 행 높이에 맞는 작은 구현으로 DOM·보관량 제한 | 가변 높이/복잡한 스크롤 요구 시 라이브러리 재검토 |
| Actuator·Micrometer·Prometheus | HTTP/JVM/풀/배치 계측·시계열 보관·고정 조회 | 업무 데이터 저장소 대체가 아니며 관측 자원/보관 상한 필요 |
| Alertmanager | 지속 경보의 그룹화·중복 억제·발생/해소 전달 | 내부 수신 데모. 외부 SMS/메일이나 영구 장애 이력은 아님 |
| Keycloak·Spring Security | 표준 로그인·서버 JWT 검증·Cluster 범위 권한, 공고 SSO 요구 | 필수 과제만이라면 생략 가능. 인증 서버 운영/공개 설정 부담 존재 |
| Docker Compose·NGINX | DB/앱/관측 환경 재현, 정적 파일·동일 출처 API 프록시 | 실제 클러스터 배포 요구가 없어 Kubernetes/Helm 운영 부담은 추가하지 않음 |
| Jenkins | 공고/사용자 선택에 맞춘 단일 파이프라인·이미지/인증/복구 검증 | GitHub Actions도 가능하나 중복 CI는 운영하지 않음 |
| JUnit·Mockito·Testcontainers | 정책 단위 테스트와 실제 PostgreSQL 스키마/SQL/트랜잭션 검증 | H2만으로 PostgreSQL 방언·인덱스 검증을 대체하지 않음 |
| Vitest·Vue Test Utils·jsdom | 비동기 조회·컴포넌트·폴링 상태 회귀 | 실제 브라우저 렌더링 성능은 측정하지 못함 |
| Playwright·Chromium | 실제 API·로그인 E2E, CPU/cache 조건의 반복 측정 | headless 결과는 실제 Chrome 작업관리자 메모리/FPS 검증과 구분 |

Redis·Kafka·Elasticsearch·MSA는 현재 해결할 요구가 없어 추가하지 않았습니다. 실제 Kubernetes API도 연결하지 않았으며 Auknowlog의 pgvector·Langfuse와 이 독립 과제의 스택을 혼동하지 않습니다.

추가 질문의 실제 DB 제한 조회·포트/컨테이너 격리·계정 보관과 전체 구성도는 [전체 구성 해설](PROJECT_ARCHITECTURE.md)에 정리합니다.

## 5. 자체 가상 리스트·제한 캐시

**서버 페이지 조회, 브라우저 데이터 보관, DOM 생성은 서로 다른 세 경계**입니다. 한 가지만 제한하면 다른 단계에서 병목이 생길 수 있습니다.

| 경계 | 현재 제한 | 해결하는 문제 |
|---|---|---|
| 서버 → 브라우저 | 목록/검색 응답 최대 100개 | 15만 JSON 전송/파싱 방지 |
| 목록 캐시 | 최근 5페이지, 최대 500개 | 오래 탐색할수록 데이터가 계속 쌓이는 문제 방지 |
| 실제 DOM | 보이는 범위와 앞뒤 5행 | 500개를 보관해도 모든 행의 레이아웃/그리기를 하지 않음 |
| 계층 캐시 | 부모 페이지 24개, 동시 펼침 8개 | 여러 계층을 열면서 캐시/행이 무제한 증가하는 문제 방지 |

### 가상 리스트의 예

한 행이 60px이고 목록 표시 영역이 600px이라면 눈에 보이는 행은 약 10개입니다. 보관 데이터가 500개여도 가운데를 보고 있을 때는 앞뒤 각 5개를 더해 약 20개 행만 생성합니다. 맨 위/끝에서는 경계에 맞춰 더 적게 생성합니다. 트리는 행 높이 44px을 사용합니다.

현재 스크롤 위치로 시작/끝 인덱스를 계산해 `items.slice(start, end)` 범위만 Vue가 렌더링합니다. 빈 공간 요소는 **현재 보관 중인 데이터 수 × 행 높이**만큼 높이를 확보하고 보이는 묶음은 `translateY`로 배치합니다. 따라서 목록 500행이면 예시 높이는 30,000px이지 전체 15만 행 길이의 스크롤바가 아닙니다. 스크롤 계산은 requestAnimationFrame에 모으고 실제 영역 높이는 ResizeObserver로 반영합니다.

DOM은 브라우저가 관리하는 문서 요소 구조이며 Vue 컴포넌트/이벤트·스타일/레이아웃 비용과 연결됩니다. 가상화는 내려받은 모든 데이터의 메모리를 없애는 기능이 아니라 **표시할 요소 수를 제한**하는 기능입니다.

### 제한 캐시의 예

100개씩 다섯 페이지를 보관한 뒤 여섯 번째를 받으면 첫 번째를 버립니다. 이후 목록 보관 창은 101~600번째이며, 제거한 행 높이만큼 스크롤을 보정합니다. 캐시에서 제거한 맨 앞부분을 다시 무한 스크롤해 볼 수는 없고 `처음부터`로 재조회합니다. 현재는 임의의 100,000번째 행으로 점프하는 UX가 아닙니다.

500개는 **주 목록 캐시 정책**이지 트리/상세/요청 중 임시 응답까지 합친 모든 JavaScript 객체 수나 브라우저 전체 메모리의 절대 상한이 아닙니다. 갱신 중에는 기존 창과 교체 응답이 잠시 함께 존재할 수 있습니다. 계층은 별도 24페이지·페이지 50개(검색 위치 고정 시 51개)로 제한합니다. 테스트의 10만 숫자 배열은 가상화 범위를 검증하는 fixture이며 실제 화면이 15만 API 행을 받아 둔다는 뜻이 아닙니다.

구현과 UX 제한은 [화면 설계](FRONTEND_RENDERING.md), 데이터 조회와의 연결은 [전체 구성 해설](PROJECT_ARCHITECTURE.md)을 참고합니다.

## 6. Actuator와 Micrometer

둘 다 백엔드 안에 포함되는 Java 라이브러리이며 Prometheus처럼 별도 컨테이너 서비스가 아닙니다.

| 구성 | 역할 | 예 |
|---|---|---|
| Micrometer | 애플리케이션의 측정값을 등록·기록하는 공통 계측 API | 요청 횟수·처리 시간·heap·연결 풀 값 |
| Spring Boot Actuator | 관리 기능과 endpoint 제공, Micrometer/프레임워크 계측 연동 | `/actuator/health`, `/actuator/prometheus` |
| Prometheus registry | Micrometer의 값을 Prometheus 형식으로 제공하는 연동 | `http_server_requests_seconds_count` 등 |
| Prometheus 서버 | endpoint를 읽어 시간별 표본을 저장하고 PromQL·규칙 평가 | 증가량·P95 추이·지속 경보 |

비유하면 Micrometer는 계기와 기록 도구, Actuator는 계기를 확인하는 관리 창구, Prometheus는 주기적으로 읽어 시계열을 보관하는 시스템입니다. Actuator가 직접 업무 테이블을 훑어 지표를 만드는 것은 아닙니다.

### 자동 계측과 직접 계측

- 자동 연동: Spring HTTP 요청 지연·횟수, JVM 메모리, HikariCP 연결 수 등입니다. Mock 리소스 상태가 아니라 실행 중인 서버 자체의 실제 값입니다.
- 직접 계측: `ResourceService.observe`가 목록/검색 Repository 구간을 `Timer`로 감싸고 성공/실패·행 수를 기록합니다. Mock 배치 시간·성공 커밋 변경량·실패 횟수도 서비스 코드에서 기록합니다.
- `Counter`는 증가하는 누적값, `Timer`는 처리 횟수·총 시간과 설정된 시간 분포, `Gauge`는 heap/활성 연결처럼 현재 변하는 값을 표현합니다. Histogram 버킷은 설정을 켠 Timer 등에 노출되며 P95 근사 계산에 사용합니다.
- 사용자 ID·리소스 이름·검색어를 label로 붙이지 않고 유형·동작·성공 여부 같은 제한된 값만 사용해 시계열 증가를 억제합니다.

요청 → HTTP/조회 계측 → 메모리의 MeterRegistry 갱신 → Actuator 지표 노출 → Prometheus 수집·저장 → 고정 PromQL → 운영 화면 순서입니다. 프로세스를 재시작하면 JVM 내부 누적 Counter는 초기화되지만 Prometheus의 이전 시계열이 즉시 지워지는 것은 아닙니다. `rate`/`increase`는 Counter 재시작을 고려한 조회 함수이며 단순 최신값 차감과 구분합니다.

### 관리 포트의 보안 경계

현재 설정은 health/prometheus endpoint만 노출합니다. 개발 관리 포트는 127.0.0.1:8086, runtime/auth는 컨테이너 내부 8086입니다. NGINX의 `/actuator/` 경로는 404로 차단합니다. 일반 화면 포트로 모든 관리 기능을 공개한 구조가 아닙니다.

실제 수집 정의는 [운영 관측](OPERATIONS_AND_DELIVERY.md)을 참고합니다.

## 7. Alertmanager는 무엇인가요?

네, Prometheus 생태계의 별도 오픈소스 프로그램입니다. 이 프로젝트에서는 별도 Docker 컨테이너로 실행합니다. **Prometheus는 수치를 수집하고 경보 조건을 판단하며, Alertmanager는 받은 경보를 어떻게 묶고 언제 어디로 전달할지 관리합니다.**

| 단계 | 이 프로젝트의 역할 |
|---|---|
| Micrometer/Actuator | 실패 횟수 등의 계측·노출 |
| Prometheus | 시계열 저장, PromQL로 조건 평가, 지속 여부에 따른 규칙 상태 관리 |
| Alertmanager | 경보 그룹화·반복 간격·중복 알림 억제·관련 경보 억제·해소 전달 |
| 독립 수신기 | webhook 발생/해소 이벤트 수신, 최근 200개만 메모리 보관 |
| 운영 경보 화면 | Prometheus의 규칙 상태를 조회. Alertmanager 전달 이력을 직접 조회하는 화면은 아님 |

### 실제 세 가지 경보

1. 백엔드 지표 수집 실패/대상 시계열 없음이 1분 지속합니다.
2. 최근 5분 리소스 API 요청이 20건 이상이면서 5xx 비율이 10% 초과인 조건이 1분 지속합니다.
3. 최근 5분 Mock 배치 실패 증가량이 3회 이상인 조건이 1분 지속합니다.

여기서 배치 실패는 트랜잭션/실행 실패이며 Mock Pod를 ERROR로 바꾸는 정상 시뮬레이션과 다릅니다. 낮은 요청 수의 오류율 과장을 막으려고 최소 요청 수 조건을 둡니다. 수집 실패도 DB 장애라는 단정은 아닙니다.

### 화면 상태와 알림 전달의 차이

- **조건 미충족(inactive):** 해당 경보 조건이 성립하지 않습니다. 전체 서비스 정상 보장은 아닙니다.
- **지속 여부 확인 중(pending):** 조건이 성립했지만 지속 조건을 아직 채우지 않았습니다.
- **경보 발생(firing):** 조건이 필요한 시간 동안 유지됐습니다.
- **해소(resolved):** 발생했던 경보가 해소되어 Alertmanager가 해소 알림을 보냅니다. UI는 다시 inactive로 보일 수 있습니다.

Prometheus는 주기적으로 평가하므로 실제 장애 발생부터 정확히 60초에 알림이 오는 것은 아닙니다. 수집·평가·그룹 대기/전달 시간이 포함됩니다.

현재 Alertmanager는 job/경보 이름으로 묶고 최초 그룹 대기 5초, 그룹 변경 전달 간격 15초, 같은 경보 반복 4시간을 설정했습니다. 백엔드 수집 실패 경보가 발생하면 같은 대상의 API/Mock 경보 알림을 억제합니다. 원인과 관련된 알림 폭주를 줄이기 위함이며 Prometheus 규칙의 원래 firing 상태까지 지우지는 않습니다.

### 왜 백엔드와 독립 수신기를 사용하나요?

백엔드가 죽으면 같은 백엔드를 사용하는 화면도 오류를 낼 수 있습니다. 따라서 Prometheus → Alertmanager → 별도 수신기 경로로 알림을 전달합니다. 다만 Mac/Docker 전체가 중단되면 함께 멈추는 단일 호스트이며 외부 감시/고가용성을 구현한 것은 아닙니다.

현재는 외부 이메일/SMS/Slack 발송이 아니라 내부 webhook 데모이고 수신기 재시작 시 메모리 이력은 사라집니다. 장기 장애 이력·자동 복구·사용자 알림 설정 화면은 포함하지 않습니다. 구성과 이전 실제 장애/복구 검증은 [경보 설계](ALERTING_AND_RECOVERY.md), 연결 그림과 PromQL 예시는 [전체 구성 해설](PROJECT_ARCHITECTURE.md)에 있습니다. 다음 학습은 **8번 테스트 도구와 빌드 과정**입니다.

### 추가 질문: 수집 실패/대상 시계열 없음과 내부 수신기

`up=0`은 Prometheus가 설정된 Actuator 수집 요청에 실패했다는 뜻입니다. 연결 거부·시간 초과·HTTP 오류·지표 해석 실패 등을 포함하며 DB 장애로 단정하지 않습니다. `absent(up{job="infrastructure-api"})`는 그 대상의 up 시계열 자체가 조회되지 않는 상태입니다. 대상 설정이 없거나 사라진 경우 등이 있으며 Prometheus 자체가 중단된 상황을 Prometheus가 계속 평가할 수 있다는 뜻은 아닙니다.

HTTP 수집 성공이지만 업무 요청이 0건인 것은 수집 실패가 아닙니다. 정상적으로 읽은 본문에 특정 지표가 없다는 뜻과도 다릅니다. 유효한 빈 지표 응답도 up=1일 수 있으며 현재 규칙은 개별 heap/조회 지표의 누락까지 검증하지 않습니다. 개별 필수 지표 누락 감지는 별도 규칙이 필요합니다.

앱의 ADMIN `운영 관측 → 운영 경보`는 Prometheus의 규칙 상태를 보여줍니다. Alertmanager는 발생/해소 webhook을 내부 수신기의 `/webhook`으로 보내고, 수신기는 `/events`에서 최근 200개를 JSON으로 제공합니다. 이 수신기는 호스트 포트를 공개하지 않아 알림창/메일이 사용자에게 자동으로 뜨는 구조가 아닙니다. 직접 확인은 같은 Compose 네트워크 내부에서 수행합니다. 이 프로젝트에 별도 수신함 화면은 없습니다.

### 추가 질문: 120초 토큰·PromQL·Prometheus의 필요성

현재 Access Token은 JWT이고 수명은 120초입니다. 정확히 120초마다 타이머로 갱신하는 것이 아니라 API 요청 전에 `updateToken(30)`으로 남은 시간을 확인해 부족하면 갱신합니다. 사용 중이면 만료 약 30초 전부터 갱신할 수 있고 API 요청이 없으면 매 120초 정기 통신이 보장되는 구조가 아닙니다.

화면용 PromQL은 백엔드 `PrometheusOperations`의 고정 표현식 목록, 경보용 식은 `infra/prometheus/alerts.yaml`에 작성되어 있습니다. 브라우저가 임의 조회식을 보내지 않습니다. Micrometer는 현재 프로세스의 계측값, Actuator는 그 값의 관리 endpoint를 제공합니다. Prometheus는 과거 시간별 수치를 디스크에 보관하고 범위 조회·증가량/P95 계산·경보 규칙 평가를 합니다. 화면을 닫아도 서비스들이 실행 중이면 수집/평가는 계속됩니다. 현재 값만 읽는 서비스에는 필수는 아니지만 이 프로젝트의 30분 추이·5분 통계·지속 경보에는 해당 역할이 필요합니다. 구현된 보관 상한은 7일 또는 256MB이며 개별 프로세스 계측만으로 과거 시계열 저장을 대체하지 않습니다.

## 8. 테스트 도구와 빌드 시 실행 과정

### 서버: JUnit 5·Mockito·Testcontainers

| 도구 | 역할 | 이 프로젝트 예시 |
|---|---|---|
| JUnit 5 | 테스트 메서드 실행·준비/정리 생명주기·assert 검증 | 커서 검증, API 400/404/503, JWT·조회 정책 |
| Mockito | 필요한 협력 객체를 대체하고 응답/호출을 통제 | Repository 실패/반환을 정해 서비스 정책·검증 순서 확인 |
| Testcontainers | 테스트에 필요한 실제 의존 서비스를 Docker로 임시 실행 | 실제 PostgreSQL에서 Flyway·15만 seed·JOIN/SQL·트랜잭션/롤백·권한 범위 확인 |

JUnit은 실행 틀이고 Mockito는 대체 객체 도구이며 Testcontainers는 실제 DB 준비 도구입니다. 셋이 같은 일을 하거나 모든 테스트가 Docker를 쓰는 것은 아닙니다. PostgreSQL 컨테이너는 테스트 생명주기에 맞춰 준비/정리하고 해당 클래스의 여러 테스트가 공유할 수 있습니다. 운영 API 요청마다 만들거나 실제 서비스의 모든 시작 전에 테스트 컨테이너를 만드는 구조가 아닙니다.

Spring MockMvc 테스트는 실제 네트워크 브라우저 요청이 아닌 Spring 내부 요청 실행으로 HTTP 계약/보안을 검사할 수 있습니다. Testcontainers의 실제 PostgreSQL 및 서명/JWKS 검증과 결합하지만 실제 Vue→프록시→API→Keycloak 전체 동작은 별도 E2E로 확인합니다. Mockito 대체 응답을 실제 DB 검증으로 설명하지 않습니다.

### 화면: Vitest·Vue Test Utils·jsdom

| 도구 | 역할 | 검증 범위 |
|---|---|---|
| Vitest | TypeScript/JavaScript 테스트 실행·mock·가짜 타이머 | 응답 순서·취소·시간 제한·폴링 주기·오류 |
| Vue Test Utils | Vue 컴포넌트를 마운트하고 props/이벤트/출력 확인 | 선택·탭·로딩·빈 결과·가상 행 수·경보 문구 |
| jsdom | Node 안에서 document/window 등 브라우저 DOM 환경 제공 | 컴포넌트 동작을 빠르게 검사. 실제 CSS 배치·그리기/FPS는 측정하지 못함 |

이 세 도구는 함께 화면 단위 테스트를 구성합니다. 진짜 Chromium은 아니므로 실제 브라우저 E2E·반응형 캡처와 성능 검증을 대체하지 않습니다. Playwright는 실제 API/로그인·키보드·브라우저를 별도로 검증하며 상세 성능 측정은 9번에서 다룹니다.

### 어떤 명령이 테스트를 실행하나요?

| 명령 | 실행 내용 |
|---|---|
| `./backend/gradlew -p backend test` | JUnit/Mockito/실제 PostgreSQL 통합 테스트 |
| `./backend/gradlew -p backend build` | 컴파일·조립과 check/test. 입력이 같으면 테스트가 UP-TO-DATE일 수 있음 |
| `./backend/gradlew -p backend bootJar` | 실행 JAR 조립. 단독으로 전체 테스트를 실행하는 명령은 아님 |
| `./backend/gradlew -p backend bootRun` | 앱 실행. 테스트 자동 실행을 뜻하지 않음 |
| frontend의 `npm test` | Vitest 단위/컴포넌트 테스트 |
| frontend의 `npm run build` | vue-tsc 타입 검사와 Vite 번들. **Vitest를 자동 실행하지 않음** |
| `python3 scripts/test-auth.py` | 실행 중인 실제 인증 환경의 Chromium E2E, 비밀값 출력/trace 억제 |
| `bash scripts/check.sh full` | 빠른 게이트 → Gradle build → npm ci/test/build/audit |

CI는 고정된 Git 커밋 체크아웃에서 빠른 검사·서버/화면 테스트 → 이미지 → 격리 Compose → 실제 API/인증·복구 검증을 순서대로 실행합니다. Docker 이미지 자체의 `bootJar`/`npm run build`만으로 테스트를 수행한 것으로 취급하지 않습니다. 테스트가 실패하면 다음 단계를 중단하고 임시 검증 환경을 정리합니다. 새 커밋이 없는 현재 작업 트리는 기존 Jenkins 결과에 자동 포함되지 않습니다.

검증 범위/안전 경계는 [품질 게이트](QUALITY_GATES.md), 현재 계정/테마 검증은 [사용자 범위·로그인 테마](USER_SCOPES_AND_LOGIN_THEME.md)를 참고합니다. 다음 학습은 **9번 Playwright·Chromium과 성능 측정**입니다.

## 9. Playwright·Chromium과 성능 측정의 신뢰 범위

Playwright는 실제 브라우저를 자동 조작하는 도구이고 Chromium은 실행되는 브라우저입니다. jsdom의 DOM 모형과 달리 실제 네트워크·JavaScript·CSS·레이아웃·화면 그리기를 포함합니다. 로그인·검색·펼침·상세·권한 기능 E2E는 기능의 정확성을 검사하고, 일반 E2E 통과가 성능 목표 달성을 뜻하지는 않습니다.

별도 성능 스크립트는 CDP(Chrome DevTools Protocol)로 CPU 4x·캐시 OFF를 적용하고 프로덕션 빌드에서 기본 20회 반복합니다. 실제 DOM 조건과 두 번의 requestAnimationFrame까지 기다려 응답 수신만으로 완료하지 않습니다. API 시간/클릭-반영/검색 디바운스/로그인 전체/SSO 재진입을 구분하고 중앙값·P95·최댓값·초과 건수와 오류를 남깁니다.

이런 브라우저 자동화는 반복 회귀 측정에 적절하지만 도구 이름만으로 공인 성능 판정이 되지는 않습니다. 기기/버전/기동 상태/데이터/병렬 작업·시작/종료 조건에 따라 값이 달라집니다. 특히 가이드가 **최신 Chrome의 Performance 탭**을 지정하므로 번들 headless Chromium의 CDP 자동 기록만으로 최종 제출 조건을 모두 충족했다고 주장하지 않습니다. 최신 실제 Chrome에서 같은 CPU/cache 조건의 Performance 기록·FPS·작업관리자 탭 메모리 보완이 필요합니다. JS heap/RSS·합성 프레임은 탭 메모리/실제 표시 FPS의 대체값이 아닙니다. [측정 방법](PERFORMANCE.md), [남은 수동 확인](REMAINING_PERMISSIONS.md)을 참고합니다.

공식 근거: [Playwright CDPSession](https://playwright.dev/docs/api/class-cdpsession), [Chrome Performance](https://developer.chrome.com/docs/devtools/performance).

## 10. 변경·이력의 원자적 저장과 보관

Pod 상태를 NORMAL→WARNING으로 바꾼 뒤 이력 INSERT가 실패하면, 트랜잭션이 없을 때는 상태만 변경되고 이유를 추적할 수 없을 수 있습니다. 현재는 native CTE의 UPDATE/이력 INSERT와 한 회차의 4개 유형 변경을 JpaTransactionManager의 같은 트랜잭션으로 묶습니다. 전부 성공하면 커밋하고 한 단계라도 실패하면 전부 롤백합니다. 다음 처리 커서와 성공 지표도 커밋 확인 후 갱신합니다. `MockStateIntegrationTest`는 중간 실패·기존 유형 복구·이력 0건·같은 ID 재시도를 실제 PostgreSQL에서 확인합니다.

원자성은 Mock에서만 필요한 기능이 아닙니다. 실제 수집기를 도입해 현재 상태와 변경 이력을 DB에 같이 반영해도 같은 정합성 문제가 있습니다. 다만 이 DB 트랜잭션이 외부 Kubernetes 작업까지 함께 취소하거나 메시지 전달을 정확히 한 번 보장하는 것은 아닙니다. 현재 구현은 시뮬레이터가 만드는 DB 변경만 처리하며 실제 Kubernetes 연동은 없습니다.

이력은 전체 테이블 최신 20,000건 또는 최근 24시간 범위를 벗어나면 정리 대상입니다. 60초마다 최대 5,000건씩 삭제하므로 즉시 상한 보장은 아니며 개별 Pod당 20,000건도 아닙니다. 영구 감사 로그가 아니라 최근 운영 변화 확인용 정책입니다. Prometheus의 7일/256MB 시계열 정책과 다릅니다. [운영 설계](OPERATIONS_AND_DELIVERY.md)를 참고합니다.

## 추가 질문: PKCE·Refresh Token·Micrometer 저장·JUnit 활용

- **Keycloak**은 Apache-2.0 OSS 인증/계정 관리 서버입니다. 라이선스 비용과 실행 인프라/운영 비용은 다릅니다. [공식 저장소](https://github.com/keycloak/keycloak).
- **PKCE**는 브라우저가 임의의 verifier와 이를 SHA-256/Base64URL로 변환한 challenge를 사용해, 로그인을 시작한 클라이언트가 인증 코드를 교환하는지 확인합니다. 인증 코드만 가로챈 공격자가 토큰을 얻기 어렵게 하며 JWT 암호화 기능은 아닙니다. 현재 S256·public client를 사용합니다. [표준](https://www.rfc-editor.org/rfc/rfc7636).
- **현재 인증 환경**을 2026-10-17 읽기 전용으로 확인한 값은 Access Token 120초, SSO idle 1,800초, SSO max 36,000초입니다. client idle/max는 0으로 SSO 값을 상속하며 별도 클라이언트 수명 재정의는 없습니다. 유휴 30분·최대 10시간으로 이해하되 발급된 Refresh Token의 남은 수명/세션·최대 상한에 의존합니다. 갱신하면 idle은 연장되지만 max는 연장되지 않습니다. `updateToken(30)`은 API 직전 남은 시간이 30초 미만이면 갱신하며 정기 30초 타이머가 아닙니다. 자동 폴링도 갱신을 일으킬 수 있습니다. 새 환경은 템플릿에 명시하지 않은 Keycloak 기본값/클라이언트 설정에 따라 달라질 수 있으며 이번에 설정을 변경한 것은 아닙니다. [세션 의미](https://www.keycloak.org/docs/latest/server_admin/index.html#_timeouts).
- **Micrometer 저장 위치**는 애플리케이션 JVM의 MeterRegistry/계측 객체 메모리입니다. Counter는 누적 수, Timer는 횟수·총 시간·버킷 등 집계이며 Gauge는 JVM/연결 풀의 현재 상태를 읽습니다. 요청 원본을 전부 쌓는 단기 DB가 아닙니다. 일부 통계에는 시간 창이 있지만 모든 계측값이 동일한 기간 후 사라지는 것은 아닙니다. 재시작 시 누적 계측이 초기화될 수 있습니다. Prometheus가 Actuator에서 15초마다 스냅샷을 수집해 시간과 함께 디스크/볼륨에 보관합니다. 수집 사이 요청은 누적 통계에 반영되지만 순간 Gauge 피크는 놓칠 수 있습니다. [Timer의 시간 창](https://docs.micrometer.io/micrometer/reference/concepts/timers.html).
- **JUnit 활용**은 개수만이 아니라 실패 경계를 봅니다. 조회 limit/커서·오류 응답·JWT 위변조/권한·SQL 횟수/Entity 로딩·풀 고갈/복구·원자적 롤백·보관 정리·15만 seed 재실행을 확인합니다. 최신 저장된 서버 결과는 120개·실패/오류/skip 0(실제 PostgreSQL 49개 포함)입니다. 단위 mock만으로 끝내지 않고 실제 PostgreSQL을 포함하므로 과제 규모에서 핵심 경로를 의미 있게 활용합니다. 다만 JaCoCo/분기 커버리지 수치를 측정하지 않았고 100% 커버리지·모든 경쟁 상태/부하 상황 검증을 뜻하지는 않습니다. 이번 UI 정돈에서는 Java를 변경하지 않아 서버 테스트를 다시 실행하지 않았습니다.

### Micrometer는 결국 무엇을 얼마나 저장하나요?

핵심은 **등록된 계측기마다 현재 집계 상태를 메모리에 두고 갱신하며, 요청 원본을 시간순으로 계속 쌓지 않는다**는 것입니다. 코드나 Spring 자동 계측이 지표를 등록하고 메서드/경로/상태 등 제한된 라벨 조합마다 별도 집계를 갖습니다. 실행 중 항목이 등록될 수 있으므로 항목 수가 절대 불변인 것은 아니지만, 이 프로젝트는 리소스 ID/검색어를 지표 라벨로 넣지 않습니다.

아래는 설명용 요청 3개(10ms/20ms/50ms)이며 실제 성능 측정값이 아닙니다.

```text
요청 전      메모리의 count=0, total=0ms
10ms 요청 후 메모리의 count=1, total=10ms
20ms 요청 후 메모리의 count=2, total=30ms
50ms 요청 후 메모리의 count=3, total=80ms
```

이 과정에서 과거의 count=1/2 상태를 별도 행으로 계속 보관하는 것이 아닙니다. Timer는 분포/버킷 등 다른 통계도 유지하지만 요청 원문/개별 소요 시간 전체를 목록으로 쌓지는 않습니다. 누적 횟수/합계는 계측기/프로세스 수명 동안 유지되고, Gauge는 현재 상태를 읽으며 최대값/일부 통계에는 별도 시간 창이 있습니다.

Prometheus가 두 번째 요청 뒤 수집하면 (count=2,total=30ms)를 시각과 함께 저장합니다. 다음에 세 번째 요청 뒤 수집하면 (3,80ms)를 저장하고, 차이로 그 사이 1건/50ms를 계산할 수 있습니다. 이것이 **조회 시점의 누적 결과를 가져오더라도 수집 사이 요청이 통계에 반영되는 이유**입니다. 여러 건이 사이에 있으면 구간 합계/분포만 알 수 있고 개별 요청을 모두 재구성할 수는 없습니다. Gauge의 순간 피크나 수집 전 프로세스 종료까지 무손실로 보장하지 않습니다.

### Performance 캡처·요약·와이파이·알림 관계

- 실제 Chrome Performance 패널은 한 기록의 CPU/Network/실행 경로를 분석하는 근거입니다. 반복 표본 요약은 저장된 측정값에서 중앙값/P95/최댓값/초과 횟수를 계산한 보조 자료입니다. 요약 이미지 자체가 필수 합격 조건은 아니고 패널 캡처와 역할이 다릅니다. 실제 캡처와 측정 한계는 [원본 화면 설명](CHROME_PERFORMANCE_CAPTURE.md)을 참고합니다.
- 현재 측정은 같은 Mac의 127.0.0.1과 Docker 내부 네트워크입니다. 요청이 와이파이 AP/인터넷 서버를 왕복하는 경로가 아니므로 일반적인 와이파이 지연을 직접 원인으로 보기는 어렵습니다. CPU/VM/DB/프록시/브라우저 스케줄링을 우선 점검해야 합니다. 원격 URL·다른 기기 접속의 사용자 체감은 별개입니다. 연결 상태 변화로 자동 폴링이 멈추는 정책과 실제 패킷 지연도 구분합니다.
- 화면은 Prometheus rules 결과를 백엔드를 통해 조회합니다. Prometheus는 같은 경보를 Alertmanager에 전송하고, Alertmanager는 전달 대상/그룹화/중복·반복 간격/종속 경보 억제/해소 전달을 관리합니다. UI가 Alertmanager를 호출해 알림을 발송시키는 구조는 아닙니다.
- 현재는 job/alertname 그룹, 최초 대기 5초·변경 전달 간격 15초·지속 경보 반복 4시간·해소 전달을 사용합니다. 백엔드 수집 실패 시 관련 API/Mock 알림의 중복 전달을 억제합니다. 목적지는 내부 수신기이며 외부 메일/SMS는 설정하지 않았습니다. 상세는 [경보 설계](ALERTING_AND_RECOVERY.md)를 참고합니다.
