# Infrastructure Monitoring Service 작업 이력

최종 갱신: 2026-10-16 안정화 버전 커밋·원격 반영 · 범위: OSC 기술 과제용 독립 프로젝트

이 문서는 초기 구성부터 현재까지의 구현·검증·개선 과정을 요약하고 이후 작업을 계속 누적하기 위한 이력입니다. Auknowlog 및 이전 회사 프로젝트의 개발 이력은 포함하지 않습니다. 기존 단계별 보고서와 로컬 Git 이력을 바탕으로 작성했으며, 당시 미검증 상태와 후속 검증을 구분합니다.

현재 사용 방법과 설계는 [프로젝트 기준 문서](PROJECT_GUIDE.md), [README](../README.md)를 참고합니다. 이 문서는 **왜 어떤 작업을 했고 어떤 결과를 얻었는지**를 시간순으로 남깁니다. 새 작업 기록 규칙은 [AGENTS.md](../AGENTS.md)에 설정했습니다. 별도 백그라운드 감시나 예약 작업이 아니라, 이후 이 저장소에서 작업을 마무리할 때 함께 갱신하는 방식입니다.

## WH-001 · 요구사항과 초기 구성

- 목적: 과제 가이드와 채용 공고를 기준으로 기존 프로젝트와 독립적으로 구현하고, 실제 10만 건 규모로 조회·화면 성능을 검증합니다.
- 구성: Java 21·Spring Boot 3.x·PostgreSQL·Flyway, Vue 3·TypeScript·Vite, 로컬 Compose를 구성했습니다. 데이터 생성은 서비스와 분리된 재실행 가능한 SQL로 작성했습니다.
- 데이터 모델: 과제의 Cluster → Node → Namespace → Pod 계층과 FK·유일성·조회 인덱스를 설계했습니다. 이는 과제 모델이며 실제 Kubernetes의 Namespace/Node 관계를 그대로 재현하는 모델은 아닙니다.
- 기준: API 처리와 브라우저 초기 진입·검색·갱신·가상화의 측정 범위를 구분하고 CPU 제한, 캐시, 데이터 규모, 표본 수를 명시했습니다.
- 초기 제한: Maven 저장소 DNS, Docker 소켓, 로컬 포트·공유 메모리 권한 문제로 실제 DB·정식 빌드·브라우저 검증을 완료하지 못했습니다. 문법·Compose 구성·계층 수 계산 및 캐시 도구의 번들 검사를 실제 구동 성공으로 표시하지 않았습니다.
- 근거: [구현 계획](IMPLEMENTATION_PLAN.md), [초기 구동 보고서](VALIDATION_REPORT.md), [측정 기준](PERFORMANCE.md).

## WH-002 · 조회 API와 검색·커서 정책

- 건수, 유형별·부모별 목록, 직속 하위 목록, 상세·상위 경로, 이름 부분 검색 및 상태 필터를 구현했습니다.
- 초기 조회는 SQL 구조·바인딩·반환량을 직접 제어하는 JDBC 방식으로 작성했습니다. 이후 사용자의 JPA 전환 요청을 WH-014에서 반영했습니다.
- ID keyset 커서에 조회 조건을 연결하고 요청 최대 100개, 다음 페이지 확인용 내부 최대 101개를 적용했습니다. 잘못된 요청·커서·없는 리소스와 DB 장애 응답을 구분했습니다.
- Flyway V2에 pg_trgm 이름 GIN 인덱스와 부모/상태·ID 인덱스를 추가했습니다. 검색 파라미터 바인딩과 와일드카드 처리를 적용했습니다.
- 당시 검증: 캐시 라이브러리 환경 단위/MVC 40개 통과. 실제 PostgreSQL 통합 테스트는 작성했지만 Docker 제약으로 실행하지 못했습니다. 후속 정식 실행 결과는 WH-004에 기록합니다.
- 근거: [API 계약](API.md), [2단계 보고서](STAGE2_REPORT.md).

## WH-003 · 화면과 API 연결

- 계층 지연 펼침, 부모 범위 목록, 상세·경로, 검색·상태 필터, 빈 결과·오류·재시도 및 수동 갱신을 연결했습니다.
- 고정 높이 가상 리스트로 보이는 행과 오버스캔만 렌더링하고 최근 5페이지·500개 목록 캐시를 유지합니다. 트리 캐시와 동시 펼친 부모도 제한했습니다. 사용하지 않는 TanStack Virtual 의존성은 제거했습니다.
- 검색은 250ms 디바운스, 이전 요청 취소 및 응답 순서 검증으로 오래된 결과가 화면을 덮어쓰지 않게 했습니다.
- 당시 검증: 캐시 Vitest 환경 33개와 Vite 번들 확인. 정식 의존성·타입 검사·실제 API E2E·성능은 미검증이었고 개발 포트 바인딩도 실패했습니다.
- 근거: [렌더링 설계](FRONTEND_RENDERING.md), [3단계 보고서](STAGE3_REPORT.md).

## WH-004 · 중단 해소와 정식 실행

- 소스를 현재 독립 프로젝트 폴더로 옮기고 다른 프로젝트의 node_modules를 빌리지 않는 별도 설치·잠금 파일을 만들었습니다. 기존 프로젝트 DB·컨테이너·소스는 보존했습니다.
- Docker·네트워크·포트 제약이 해소된 환경에서 실제 PostgreSQL 17.11과 백엔드·화면을 실행했습니다. OS 보안 설정을 임의로 완화하거나 잠금 화면을 해제하지 않았습니다.
- Flyway V1~V2와 20/200/2,000/100,000개 실제 적재·재적재·조회 건수를 확인했습니다.
- 의존성 설치 과정의 npm peer 해결 오류, 테스트 선택자 및 가짜 타이머 적용 순서 문제를 수정했습니다. Vitest 수정 버전과 잠금 파일을 적용해 npm audit 0건을 확인했습니다.
- 정식 검증 당시: Maven 69개(실제 PostgreSQL 통합 17개 포함), 프론트 44개, 실제 API Chromium 5개, npm ci·타입 검사·빌드 통과. 이후 기능 추가에 따른 최신 수는 상단 요약을 기준으로 합니다.
- 근거: [실제 DB·브라우저 후속 보고서](STAGE4_REPORT.md).

## WH-005 · Mock 변경과 자동 갱신

- 실제 상태 변화를 관찰하도록 기본 비활성인 mock 프로필을 추가했습니다. 시작 10초 후부터 배치 완료 5초 뒤 다음 변경을 수행합니다.
- 한 배치 최대 Cluster 1·Node 5·Namespace 10·Pod 100개를 변경하며 전체 10만 행을 메모리에 적재하지 않습니다. 커서 순환, 상태 순환, 속성 범위 및 재시작 횟수 상한을 적용했습니다.
- 4개 유형의 변경은 한 트랜잭션으로 처리하고 실패 시 전체 롤백합니다. 현재는 WH-014의 JpaTransactionManager를 사용합니다.
- 화면은 현재 조회창·펼친 부모·선택 상세만 폴링합니다. 숨김·오프라인·사용자 해제 시 중지하고 겹친 요청을 방지하며 실패 시 최대 60초로 백오프합니다. 선택·스크롤을 유지하고 건수 집계를 반복하지 않습니다.
- 검증: 실제 DB의 배치량·속성·롤백·커서와 브라우저의 DB 변경 반영·선택·스크롤 유지 확인. Mock은 실사용 DB나 실제 Kubernetes 제어 기능이 아닙니다.
- 근거: [상태 변경·자동 갱신](LIVE_UPDATES.md), [후속 검증](STAGE4_REPORT.md).

## WH-006 · 콘솔형 UI

- Headlamp·Rancher·Lens의 탐색 패턴을 참고해 좌측 유형/계층, 중앙 열 중심 목록, 우측 상세 탭을 구성했습니다. 제품의 브랜드·화면·아이콘을 그대로 복사하지 않고 자체 SVG와 코드로 작성했습니다.
- 유형 바로가기, 현재 조회창 상태 집계, 실제 API 값의 Node meter, 상세 닫기·탭 이동, 검색 단축키와 모바일 계층 접기를 추가했습니다.
- 조회창 집계와 전체 DB 건수를 구분하고 미구현 운영 메뉴·가상 데이터를 추가하지 않았습니다.
- 당시 검증: 프론트 50개·실제 API E2E 7개 통과. API·DB 계약은 변경하지 않았습니다.
- 근거: [UI 설계·참고 출처](UI_DESIGN.md).
