# 성능 측정 프로토콜

## 공통 환경

프로덕션 빌드, 최신 Chrome, CPU 4x throttling, 브라우저 캐시 비활성화를 적용합니다. 서버·DB는 기동된 상태이며 초기 데이터 생성 시간과 서버 시작 시간은 브라우저 진입 목표에 포함하지 않습니다. 실제 기기 사양, Chrome 버전, 데이터 규모, 브라우저 확대율과 화면 크기를 기록합니다. 2026-10-14의 실제 측정과 개선 전후 결과는 [성능 검증 보고서](PERFORMANCE_RESULTS.md)에 기록했습니다.

| 항목 | 시작 → 종료 | 목표 |
|---|---|---|
| 최초 진입 | 페이지 navigation 시작 → 실제 Cluster 목록 표시 및 조작 가능 | 500ms 이하 |
| 펼침·접기 | 클릭 → 실제 하위 목록 표시 또는 접기 완료 | 100ms 이하 |
| 검색 | 디바운스 종료 → 현재 검색어 결과가 표시됨 | 300ms 이하 |
| 필터 | 조건 변경 → 필터 결과 표시 | 200ms 이하 |
| 스크롤 | 실제 10만 Pod를 탐색 가능한 가상 리스트 연속 스크롤 | 55fps 이상 |
| 갱신 | 새로고침 클릭 또는 폴링 요청 시작 → 변경값 표시 | 200ms 이하, 깜빡임 없음 |
| 메모리 | Chrome 작업관리자의 해당 탭 메모리 | 참고 목표 300MB 이하 |

최초 펼침은 네트워크 포함, 이미 로드한 계층의 재확장은 별도 기록합니다. 로딩 표시가 보인 시점을 조회 완료로 취급하지 않습니다. 폴링 탐지 지연은 갱신 반영 지연과 구분해 별도 기록합니다. CPU 제한은 개발자도구 설정이며 네트워크 제한은 지정되지 않았으므로 별도 적용 여부를 명시합니다.

## 측정 자료

3단계 화면은 전역 Pod를 100개씩 순차 조회하고 최근 5페이지·500개를 가상화합니다. 임의 10만 번째 위치 점프는 제공하지 않습니다. 제출 전 이 탐색 UX가 과제 기대에 부합하는지 확인합니다. 실제 DB의 10만 건을 연결한 상태에서 캐시 내 스크롤 FPS, 다음 페이지 네트워크 대기, 페이지 제거 시 스크롤 보정, 반복 탐색 메모리를 별도로 기록해야 합니다. jsdom에서 만든 10만 숫자 항목의 DOM 상한 테스트를 DB·Chrome 성능 측정으로 대체하지 않습니다. [화면 설계](FRONTEND_RENDERING.md)를 참고합니다.

- Chrome Performance 기록과 FPS 관측
- API·DB·렌더링 구간별 보조 측정
- 반복 측정 횟수, 중앙값·상위 지연·최댓값과 실패 사례
- 초기·반복 탐색 후 메모리와 DOM 노드 수
- 쿼리 실행 계획과 반환 행 수

Playwright 실행 시간이나 API 응답 시간만으로 브라우저 성능 목표 달성을 주장하지 않습니다. 아래 자동 측정은 실제 DOM 조건 충족 뒤 두 번의 requestAnimationFrame을 기다려 화면 반영 기회를 포함합니다. 광학적 표시 시점의 직접 측정은 아니며 로딩 표시만으로 종료하지 않습니다.

## 재현 명령과 측정 경계

Compose DB에 seed를 적재하고 API 8081을 실행한 뒤 프론트 프로덕션 빌드를 preview로 제공합니다. 측정은 이 프로젝트의 Pod 1 상태를 실제로 변경하므로 격리된 과제 DB에만 실행합니다. 외부 서비스·AI API 호출은 없습니다.

```bash
cd frontend
npm ci
npx playwright install chromium
npm run build
npm run preview
```

다른 터미널에서:

```bash
cd frontend
PERF_LABEL=local-check npm run test:performance
```

- 각 탐색 시나리오를 20회 반복하며 `PERF_REPETITIONS`로 3~50회를 선택할 수 있습니다. 새 브라우저 context·캐시 OFF·CPU 4x를 적용합니다. 같은 Chromium 프로세스를 재사용하므로 첫 V8·브라우저 초기화와 이후 탐색은 구분해 기록합니다.
- 최초 진입은 navigation부터 Cluster 루트·Pod 첫 목록·전체 건수의 표시까지 측정합니다. Cluster만의 표시 시점도 별도 기록합니다. 펼침은 네트워크 포함 첫 요청과 캐시 재사용을 나눕니다.
- 검색은 250ms 디바운스를 제외한 요청 시작부터, 필터·수동 갱신은 UI 이벤트 시작부터 실제 변경 결과 표시까지 측정합니다. 변경 없는 화면을 갱신 완료로 판단하지 않습니다.
- 5페이지·500개 창의 갱신도 따로 20회 측정합니다. 스크롤은 4초 연속 수행하며 CDP trace의 `DirectRenderer::DrawFrame` 수·시각으로 합성 프레임률을 계산하고 RAF 간격과 함께 기록합니다. 하드웨어 디스플레이의 실제 표시 프레임률과 같다고 주장하지 않습니다.
- 추가 100페이지·10,000개 순차 탐색에서 DOM·500개 캐시·JS heap·renderer RSS를 25페이지마다 기록합니다. 강제 GC 결과는 별도 보조 값이며 일반 메모리 사용량으로 대체하지 않습니다. RSS와 JS heap은 Chrome 작업관리자의 탭 메모리와 다른 지표입니다.
- 원본 JSON·trace는 `frontend/.validation/performance/`에 생성됩니다. 핵심 결과와 SQL 실행 계획 요약은 보고서에 보관합니다. 실패를 제거하지 않고 오류·목표 초과 횟수를 함께 남깁니다.

DB 실행 계획은 프로젝트 루트에서 다음과 같이 확인합니다. 대표 검색·필터·커서·단문 검색·집계 SQL이며, 투영 열과 경로 표현이 실제 API 전체 쿼리와 동일한 것은 아닙니다.

```bash
docker compose exec -T db psql -U monitoring -d monitoring -v ON_ERROR_STOP=1 < scripts/explain.sql
```
