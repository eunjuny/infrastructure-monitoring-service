# 성능 측정 프로토콜

## 환경과 목표

프로덕션 화면, 초기 적재가 끝난 PostgreSQL, 실행 중인 Spring Boot·Keycloak을 사용합니다. Chrome·기기·데이터 규모·뷰포트·CPU/cache·네트워크 조건을 매 실행에 기록합니다. 공개 기준은 Apple M1 Pro/16GB·15만 Pod·CPU4×·캐시 비활성화·네트워크 제한 없음입니다.

| 항목 | 측정 구간 | 목표 |
|---|---|---|
| 첫 화면 | 문서 navigation→Cluster 첫 목록 표시·조작 가능 | 500ms 이하 |
| 펼침·접기 | 클릭→실제 하위 행 표시·제거 | 100ms 이하 |
| 검색 | 디바운스 종료/요청→현재 검색어 결과 표시 | 300ms 이하 |
| 필터 | 선택 변경→결과 표시 | 200ms 이하 |
| 갱신 | 수동 클릭/자동 요청→변경된 목록·선택 상세 반영 | 200ms 이하 |
| 스크롤 | 대량 Pod 탐색 중 Chrome FPS 미터 | 55fps 이상 |
| 메모리 | Chrome 작업관리자 해당 탭 | 참고300MB 이하 |

첫 펼침은 네트워크 요청을 포함하고 캐시 재펼침과 구분합니다. 폴링의 다음 주기까지 대기와 요청 후 화면 반영 지연은 별도로 측정합니다. 로그인 비밀번호 입력·서버 부팅·초기 seed 시간은 첫 목록 준비 구간과 합치지 않습니다.

## 실제 Chrome Performance 기록

1. 관리자 로그인 후 DevTools Performance에서 CPU4× slowdown, 캐시 비활성화, 네트워크 제한 없음을 확인합니다.
2. 기록 초기화가 끝난 뒤 한 동작을 실행합니다. 같은 시간에 빌드·다른 브라우저 검증을 실행하지 않습니다.
3. 첫 목록/계층은 제품의 User Timing, 검색/필터/갱신은 테스트 도구의 mark/measure로 실제 결과 표시 경계를 확인합니다.
4. 녹화 종료 후 해당 measure의 Summary Duration을 캡처합니다. 전체 녹화 길이나 INP로 각 동작의 완료 시간을 대신하지 않습니다.
5. FPS 미터·작업관리자는 별도 관측으로 보관합니다. raw trace/HAR에는 인증 정보가 포함될 수 있으므로 공개하지 않습니다.

[목표별 실제 원본](CHROME_PERFORMANCE_CAPTURE.md)과 README 표는 동일한 이벤트 Duration을 사용합니다. 순간 FPS 관측은 전체 구간 최솟값 증명과 다릅니다.

## 반복 검증

프로젝트 루트에서 실행합니다.

```bash
PERF_BROWSER=chrome PERF_FULL=1 PERF_REPETITIONS=20 \
  PERF_LABEL=<새-이름> python3 scripts/test-auth.py --performance
```

- `PERF_BROWSER=chrome`은 설치 Chrome, 생략하면 번들 Chromium입니다. 서로 다른 브라우저 결과는 하나의 통계로 합치지 않습니다.
- 실제 PKCE 로그인, 매 회차 새 context·CPU4×·캐시 OFF·1440×1000으로 관리자 권한과20/200/2,000/150,000 건수를 확인합니다.
- 일반 동작20회, 변경 자동 갱신3회입니다. `PERF_REPETITIONS`는3~50을 허용합니다. API 시간만으로 화면 완료를 판정하지 않고 결과 DOM·유휴 상태와 두 animation frame을 확인합니다.
- `PERF_FULL=1`은 이 과제 DB의 Pod1 상태·시각을 잠시 변경해 실제 반영을 확인합니다. 마지막 테스트 값과 일치할 때만 원복해 동시 변경을 덮어쓰지 않습니다. 실사용 DB에 실행하지 않습니다.
- 500개 캐시의10초 스크롤은 CDP/RAF 보조 계측이며 native FPS 미터·탭 메모리 관측과 구분합니다.
- 종료 코드는 측정 오류·권한/건수 불일치·목표 초과를 실패로 반환합니다. 표본을 제외하거나 목표를 완화하지 않습니다.
- 원본은 Git 제외 `frontend/.validation/performance/`에 실행별로 저장하며 기존 label은 덮어쓰지 않습니다. URL query·JWT·헤더·비밀번호는 저장하지 않습니다.

공개 반복 결과와 전체 표본은 [측정 결과](FINAL_PERFORMANCE_REVIEW.md), [JSON](performance/2026-10-18-reboot-final.json)에 있습니다. 해당 실행의 관측이며 모든 환경·모든 실행의 지연 상한을 보장하지 않습니다. 후속 측정에서는 간헐 초과가 관측된 실행과 재현되지 않은 실행이 모두 있었고, 단일 원인/재발 방지는 미확정입니다. 성공 표본만 골라 반복 통계를 만들지 않습니다.

## 추가 조회 창과 집계

`frontend`에서 `PERF_LABEL=<새-이름> npm run test:performance:edges`는 짧은/미일치 검색어·전체 유형 검색,8개 부모 펼침과 최대 조회 창의 자동 갱신을 측정합니다. 연결할 실제 API·포트는 실행 모드에 맞춰 확인합니다.

목록5페이지·계층 루트와8개 부모·선택 상세는 기본15개 GET이며, 전체 건수의60초 만료가 겹치면 summary1개가 추가될 수 있습니다. 집계 제외15개 요청의 결과를 집계 포함16개 요청 그룹의 성능으로 설명하지 않습니다. 전체 건수의1분 후 실제 재요청·실패/취소 보존은 기능 E2E/단위 테스트로 별도 검증합니다.

HTTP 응답 대기에는 프록시·서버·DB·실행 대기가 포함됩니다. 브라우저 요청·본문 수신·관측 전달 지연과 SQL·GC 계측은 같은 시간축의 근거가 있을 때만 원인 분석에 연결합니다. 기기 자원 경합 가능성만으로 목표 초과를 제외하지 않습니다.
