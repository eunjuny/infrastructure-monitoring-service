# 간헐 성능 초과 조사

조사일: 2026-10-18 · 대상 커밋: `0053bcd` · GPU 확대 및 전체 건수 주기 조회가 반영된 인증 Compose

## 결론

현재 설치 Chrome에서 20회, 번들 Chromium에서 추가 5회를 실행한 결과 응답 목표 초과를 재현하지 못했습니다. 앞선 두 실행의 실패를 취소하거나 제품 코드 수정으로 해결한 결과는 아닙니다. **지속적인 성능 저하는 확인되지 않았지만, 간헐 지연의 단일 원인과 재발 방지까지 검증한 상태도 아닙니다.**

앞선 초과에서는 화면 JavaScript의 긴 실행보다 HTTP 응답 대기 구간이 큰 비중을 차지했습니다. 응답 대기는 프록시·서버·DB·프로세스 실행 대기를 포함하므로 이를 DB 쿼리 시간이나 Mac 사양 문제로 단정하지 않습니다.

## 실행별 빈도

모두 같은 Mac·15만 Pod·실제 관리자 PKCE 로그인·1440×1000·CPU4×·캐시 OFF·네트워크 제한 없음입니다. 서버는 기동된 상태이며 매 회차 브라우저 context는 새로 생성합니다. 아래 후속 두 실행은 빌드·게이트·다른 E2E와 겹치지 않았지만 사용자 앱과 다른 프로젝트를 임의 종료하지는 않았습니다.

실행 시점·프로세스 준비 상태·브라우저가 다른 소수 표본입니다. 이를 합쳐 실제 서비스의 실패 확률로 일반화하지 않습니다. 전체 표본과 통계는 [측정 자료](performance/2026-10-18-outlier-audit.json)에 보관합니다.

## 초과가 발생한 구간

1. 첫 실행의 첫 펼침208.1ms 중 하위 목록의 브라우저 응답 대기는168.63ms, 본문 수신은0.52ms였습니다. 해당 문서의 long task 관측은0건입니다.
2. 두 번째 실행의 첫 변경 자동 갱신203.2ms 구간에서 상세 응답 대기166.88ms·본문1.45ms, 목록 응답 대기는 약119ms였습니다. 문서에 기록된57ms long task는 이 초과 구간이 아닌 이후 시점에 발생했습니다.
3. 따라서 대량 DOM 생성이나 큰 본문 전송이 이번 두 초과의 주된 증거는 아닙니다. 서버 쪽 준비/JIT·GC·DB 처리·호스트 스케줄링/페이지 인 등의 가설은 남아 있습니다. 요청별 서버 trace·SQL 실행 시간과 OS 이벤트를 동기화하지 않았으므로 특정 하나를 확정하지 않습니다.

## Mac과 컨테이너 상태

조사 시점에 선택된 항목만 읽었으며 프로세스 종료, 시스템 설정 변경, Docker 전체 재시작이나 데이터 초기화는 하지 않았습니다.

- Apple M1 Pro, 논리 CPU8개, RAM16GiB. Docker VM은 CPU8개·메모리 약7.66GiB를 사용할 수 있는 설정입니다. 이는 모두 실제 사용 중이라는 뜻은 아닙니다.
- 호스트 스왑 사용량 약2.79~2.80GiB, load average 관측값 약4.26~6.86. 여러 앱과 다른 프로젝트 컨테이너가 함께 실행 중이었습니다. 스왑 누적 사용량이나 load 값만으로 해당 요청의 지연 원인을 확정할 수 없습니다.
- 관측 사이 swap-in 누적값은 증가했지만 swap-out은204,284로 유지됐습니다. 메모리 페이지 접근은 있었으나 열 경고·전력/성능 경고는 조회 결과 없었습니다. 각 초과가 발생하던 과거 순간의 OS 상태를 기록한 것은 아닙니다.
- 백엔드·DB 컨테이너는 OOM 종료 없음·재시작0회. 백엔드 cgroup CPU quota throttling 및 memory OOM 카운터0이었습니다. 호스트 전체의 CPU 경합이나 메모리 대기까지 없었다는 뜻은 아닙니다.
- 조회 시 Hikari pending0, 연결 획득의 관측 최대 약7~32ms, young GC pause 최대19ms였습니다. 이 계측은 시간 창 집계/별도 시점이므로 과거 초과 요청의 원인 추적으로 대체하지 않습니다.

이 Mac에서 동일 기준의20회가 통과했으므로 지속적인 하드웨어 성능 부족의 증거는 없습니다. 반대로 간헐 초과를 사양 문제로 제외할 근거도 없습니다. 가이드의 CPU4×·캐시 OFF 조건을 유지하고 같은 조건의 전체 표본으로 판단합니다.

## 대응과 검증 범위

- 제출 기준 비교에는 설치 Chrome을 명시하고 브라우저 버전을 결과에서 확인합니다. 번들 Chromium 결과와 합산하지 않습니다.
- 제품 코드·API·쿼리·목표값·표본 선택을 바꾸지 않았습니다. 이번 조사는 재현 여부와 지연 구간을 확인한 것이며 성능 결함의 수정 완료 보고가 아닙니다.
- 확인되지 않은 원인을 이유로 캐시·인덱스·JVM 메모리나 Docker 할당량을 임의 변경하지 않았습니다. 특히 호스트가16GiB인 상황에서 Docker 메모리를 늘리는 것이 호스트 경합을 줄인다고 단정할 수 없습니다.
- 후속 원인 확정이 필요하면 동일 Chrome의 실행 중 각 동작 시각, 프록시 upstream 시간, 서버/SQL 구간, OS 페이지 인·CPU 대기를 같은 시간축으로 수집합니다. 사용자 앱을 종료하는 비교 실험은 사용자와 범위를 정한 뒤 진행합니다.
- README는 승인된 내용과 기존 DevTools 증거를 유지했습니다. 새 headless 반복을 native 캡처로 바꾸어 설명하지 않습니다.
