# 기능 유지형 리팩터링 성능 검증

측정일: 2026-10-17 · 대상: 변경 이력 서비스 분리와 Prometheus 고정 조회식 사전 조립

## 결론

현재 측정에서는 큰 성능 회귀나 응답 오류를 발견하지 않았습니다. 리팩터링 후 초기 화면 20회 모두 500ms 이내이며 최대 227.9ms였습니다. 다만 모든 항목이 빨라진 것은 아닙니다. 최대 100개 이력 조회의 단일 요청 P95는 9.81→12.25ms, 초기 화면 P95는 216.0→226.3ms로 소폭 증가했습니다. 반복 문자열 연산 제거만으로 사용자 체감 속도가 크게 개선됐거나 통계적으로 유의한 차이가 있다고 주장하지 않습니다.

[전체 표본·환경·JAR 해시·중간 시도·정리 결과](performance/2026-10-17-refactor-comparison.json)를 함께 보관합니다. 아래 수치는 이번 격리 환경의 결과이며 과거 Vite preview·인증 환경의 성능 기록을 덮어쓰지 않습니다.

## 비교 조건과 안전 경계

- 전: 기존 `c9dd4aee8348121282256187f7e549895a95aeb0`의 backend를 `git archive`로 별도 임시 폴더에 추출해 같은 Gradle Wrapper로 `bootJar` 빌드.
- 후: WH-029에서 테스트를 통과한 현재 미커밋 작업 트리의 JAR. 두 JAR SHA-256을 결과 JSON에 기록했습니다. 원본 브랜치·Git 이력을 변경하지 않았습니다.
- Apple M1 Pro·16GiB, Java 21.0.2·Spring Boot 3.5.16·PostgreSQL 17.11. 두 JVM 모두 `-Xms128m -Xmx256m`입니다.
- 새 tmpfs PostgreSQL 하나에 20 Cluster·200 Node·2,000 Namespace·100,000 Pod와 Pod 1의 변경 이력 500개를 적재해 두 버전이 공유합니다. Mock는 끄고 동일 데이터를 조회하며 실제 사용 DB는 측정 대상으로 지정하지 않습니다.
- 백엔드 API 18091/18092·관리 18096/18097·화면 5274/5275는 모두 별도 루프백 포트입니다. 기존 5174·8081 서버와 DB는 그대로 유지했습니다.
- 화면은 **동일한 프로덕션 dist**를 두 개의 같은 정적 HTTP/API 프록시로 제공합니다. Vite 개발 서버나 과거 측정의 preview 프록시와 같은 실행 구성이 아닙니다. 전후 비교에서는 같은 프록시를 사용합니다.
- Prometheus는 두 버전 모두 기존 로컬 9094의 실제 수집 데이터를 조회합니다. `available=true`·`up=1`·heap 양수·차트 최대 31점을 검사합니다. 소스가 독립적으로 갱신되므로 수집 시각·값은 고정된 응답 fixture가 아닙니다.
- 인증 비활성 로컬 모드의 비교입니다. 서버와 DB는 준비된 상태이며 서버 시작·seed·첫 쿼리 컴파일을 브라우저 500ms 목표에 포함하지 않습니다.

## API: 단일·동시 요청

각 API/버전/동시성별 100회, 최종 실행에서 **총 1,600건**의 HTTP 상태·응답 본문 검증을 통과했습니다. 지연은 새 TCP 연결의 요청 시작부터 본문 전체 수신까지이며 JSON 내용 검증은 그 뒤에 수행합니다. 동시성 8은 closed-loop worker 상한으로 최대 처리량 실험은 아닙니다.

각 API 첫 호출과 20회 준비 호출도 별도로 보관합니다. 본 측정은 25회씩 네 블록에서 전→후/후→전 순서를 번갈아 실행합니다. 준비 호출과 최초 응답을 삭제해 존재하지 않았던 것으로 취급하지 않습니다.

## 중간 시도와 정리

첫 실행은 API 1,600건을 완료했지만 화면 계측의 공통 `.reveal-button` 선택자가 이력 대신 계층 위치 버튼을 눌렀습니다. 타임아웃을 서비스 성능 실패로 오인하지 않고 해당 브라우저 실행만 중단했습니다. 초기 API 요약과 `complete=false`·정리 성공을 별도 보관하며 최종 브라우저 결과에 섞지 않습니다. 이어진 준비 단계는 닫힌 측정 포트의 TIME_WAIT를 사용 중인 listener로 오인해 시작 전 종료했습니다. 포트 사전 확인에 reuse-address를 적용하고 실제 listener가 있으면 계속 실패하도록 유지했습니다. 서비스 코드·API·목표는 수정하지 않았습니다.

수정한 측정 도구로 전체 비교를 다시 수행한 최종 실행은 API/화면 오류 0·`complete=true`입니다. 최종 표와 JSON은 이 실행의 모든 표본을 사용합니다. 로컬 원본·실행용 스크립트·중간 실패 자료는 Git 제외 `.local/refactor-performance/`에 남겼고, 포트·임시 archive 경로에 종속된 일회성 실행 도구를 제품/CI의 새 기능으로 추가하지 않았습니다. 휴대 가능한 표본·조건·JAR/도구 해시는 위 JSON에 보관합니다.

측정용 Java 두 개·정적 프록시와 tmpfs DB 컨테이너를 종료/제거했고 기존 Docker 컨테이너 ID와 기존 화면의 20/200/2,000/100,000 조회를 확인했습니다. 제거된 것은 이 실행이 만든 임시 DB/샘플뿐이며, 실사용 이력은 삭제하지 않았습니다. 유료 AI·클라우드·SMTP 호출이나 외부 공개는 없습니다.

이번에는 실제 Keycloak 로그인·스크롤 FPS·Chrome 작업관리자 탭 메모리·장시간 최대 처리량을 재측정하지 않았습니다. 기존 [측정 프로토콜](PERFORMANCE.md), [초기 진입 개선 기록](STARTUP_PERFORMANCE.md), [인증 성능 기록](AUTHENTICATION_PERFORMANCE.md)을 이번 결과로 대체하지 않습니다.
