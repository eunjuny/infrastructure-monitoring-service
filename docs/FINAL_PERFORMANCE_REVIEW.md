# 2026-10-18 인증 화면 최종 재검증

## 판정

이 보고서는 별도 진단 기능 V4가 같은 작업 폴더에 추가되기 **이전**의 앱/DB 기준입니다. 이후 재시작에서 기존 이미지와 새 seed의 스키마 시점 차이로 실패가 발생해 기존 이미지로 UI를 복구했습니다. 새 소스/V4는 덮어쓰거나 임의 이행하지 않았습니다. 해당 변경을 포함한 최신 전체 소스 성능은 작업 조율 후 재검증해야 합니다.

**기능 검증은 통과했으나 성능 전체 합격은 아닙니다.** CPU 4배 제한·캐시 비활성의 20회 실행에서 일부 지연 목표 초과가 남았습니다. 평균/P95가 좋다는 이유로 최댓값 실패를 합격으로 바꾸지 않습니다. [README 결과 표](../README.md), [전체 표본·실행별 요약](performance/2026-10-18-final-auth.json), [측정 정의·재현 명령](PERFORMANCE.md)을 함께 확인합니다.

## 환경과 실행 구분

- Apple M1 Pro·RAM 16GiB·macOS, Node22.23.2.
- 기동된 인증 Compose의 NGINX→Spring Boot/JWT→PostgreSQL 한 서버·monitoring/identity 두 DB. ADMIN이 20 Cluster·200 Node·2,000 Namespace·150,000 Pod를 조회합니다.
- 설치된 Chrome 채널 155.0.8059.80의 headless 실행. 매회 새 context, CPU4x·캐시 OFF·서비스 워커 차단·1440×1000·별도 네트워크 제한 없음.
- 네이티브 Chrome GUI는 실행 중인 153.0.8010.53 프로세스입니다. 사용자가 업데이트 재시작 전 현재 버전 진행을 선택했습니다. 가이드의 최신 Chrome 조건까지 완료했다고 주장하지 않습니다.
- 기존 사용자 프로그램·다른 프로젝트·개발/runtime 서버는 임의 종료하지 않았습니다. 호스트 부하·Docker VM·Chrome 자동화의 영향이 포함된 로컬 측정이며, 순수 API/SQL 시간이나 분산 부하 시험과 다릅니다.

| 실행 | 표본 | 조건 | 결과 |
|---|---:|---|---|
| mail-native-baseline | 5 | 메일 반영 후·인증 성능 변경 전·읽기 전용 | 일부 목표 초과, 기준선 보존 |
| final-native-a | 20 | 변경 반영 후·FULL, 별도 네이티브 Chrome/DevTools 확인과 중첩 | 일부 목표 초과, 제거하지 않음 |

표본 수/배경 부하가 달라 전후의 엄밀한 성능 개선율을 계산하지 않습니다. A/B는 같은 코드의 반복이며 B가 빠르다는 사실만으로 코드 개선 효과라 단정하지 않습니다. 이전 [제출 화면 20회×2 결과](performance/2026-10-18-submission-ui.json)도 보존합니다.

최종 프로브의 빈 이벤트 selector 보호 후 [3회 FULL smoke](performance/2026-10-18-probe-smoke.json)도 보존합니다. 검사 오류0·Pod 원복 성공이나 자동 갱신1회가1,593.1ms로 초과해 exit1입니다. 다른 지연 목표는 3회 내 충족했지만 적은 표본으로 20회 결과를 대체하지 않습니다. 첫 수초에는 빠른 오프라인 게이트가 겹쳤으므로 성능 전후 비교가 아닌 측정 도구 재확인입니다.

## 변경한 부분

1. 공개 인증 설정 조회와 인증 JS 모듈 로딩을 병렬화했습니다.
2. Keycloak 공식 silent check-sso로 유효한 기존 세션의 앱 문서 이중 리다이렉트/로드를 줄였습니다. 세션이 없으면 정상 로그인으로 이동하며 쿠키 제한 시 공식 redirect fallback을 사용합니다. 인증 실패 시 익명 화면으로 우회하지 않습니다.
3. 갱신 시각에 기존 경량 ISO 시각 표시 유틸리티를 사용해 반복 Intl 초기화를 제거했습니다.

15만 데이터·JWT/Cluster 권한·500개 캐시 상한·초기 집계/Pod 목록 준비 조건·목표 시간은 유지했습니다. 실제 Keycloak E2E는 정상/로그아웃·SSO·권한·모바일·관리자 메일을 포함해 12개, 서버는 125개, 프론트는 89개를 통과했습니다.

## 지연 구간과 남은 점검

B의 기능/데이터 오류는 0건이며 Pod 1 상태·갱신 시각은 측정 후 원복했습니다. 수동 변경 갱신 20회·자동 변경 갱신 3회에서 목록/상세의 변경값과 빈 목록 깜빡임이 없음을 검사했습니다.

- SSO 준비 최대1,223.94ms/500ms, 첫 펼침226.9ms/100ms, 검색466.4ms/300ms, 읽기 전용 갱신671ms/200ms, 실제 변경 갱신316ms/200ms가 목표를 넘었습니다.
- 접기·캐시 재펼침·필터는 각각 20회 모두, 자동 폴링은 3회 모두 목표 내입니다. 자동 폴링의 적은 표본을 장시간 안정성 검증으로 확대 해석하지 않습니다.
- 느린 갱신에서 목록·하위 목록·집계의 요청→완료 시간이 함께 약548~594ms로 늘었고 SSO 집계는 한 번959.29ms였습니다. 브라우저에서 관측한 대기·응답 본문 처리를 포함하며 SQL 시간과 동일하지 않습니다.
- 원인이 특정 코드·DB·GC·호스트 스케줄링이라고 확정할 근거는 부족합니다. 다음은 느린 요청의 서버 처리/SQL·JVM pause와 동일 시간축의 Chrome trace를 연결하는 점검입니다. 근거 없이 캐시 TTL·비동기 표시로 정확성/준비 조건을 줄이거나 작은 데이터로 바꾸지 않습니다.

## 프레임·메모리·실제 Chrome 자료

- B의 4초 스크롤: 캐시500개·보이는19행, CDP DrawFrame59.84fps·RAF59.75fps. A는 DrawFrame60.11fps입니다. 보조 합성 프레임 계산이며 실제 디스플레이 프레임/Chrome FPS 미터 직접 관측과 구분합니다. 가이드의 FPS 미터 기준 연속 검증은 남았습니다.
- Chrome 작업관리자에서 해당 탭74.3MB를 직접 확인했습니다. 데이터15만 연결·500개 캐시, 네이티브 GUI153·DevTools 종료 상태입니다. CPU4x 반복 실행과 별도 조건이며 JS heap·renderer RSS로 대체한 수치가 아닙니다. 참고 목표300MB보다 낮습니다.
- 실제 Performance 패널 Record and reload로 초기 로드를 기록했습니다. CPU4x·Disable cache를 설정한 후 실행했지만 화면/확장 계측 오버헤드를 포함합니다. 선택 구간2.214초·FCP/LCP 약2초를 자동 반복의 SSO 준비 시간과 같다고 취급하지 않으며 합격 이미지로 제시하지 않습니다.

[실제 캡처·버전 구분](CHROME_PERFORMANCE_CAPTURE.md)을 참고합니다. 테스트 임시 탭·DevTools·작업관리자를 정리했고, 사용자 원래 탭·DB/계정·다른 프로젝트는 보존했습니다. FULL의 마지막 테스트 값이 유지된 경우에만 원복해 동시 작업 덮어쓰기를 방지했습니다. 외부 AI/SMTP 호출은 없습니다.
